2026年11月21日。ResoLove の作業ツリー（基点 `57ee8ed337`）で、投稿フォームの送信、下書きの保存・復元、結果照会を確認した。対象は初回レビューで指摘した次の3件。ブラウザーを使った受け入れ試験は統合担当が行う。

| 初回の指摘 | 修正を確認する条件 |
| --- | --- |
| 応答消失後に本文を編集すると、同じ作成キーで別の本文を送れた。どちらが確定したか判別できず、再読込後に投稿を重複作成し得た。 | 同じキーでの送信内容が初回と一致し、送信後の編集が下書きに残る。初回の拒否を確認できた場合は、修正後の本文を新しいキーで送れる。 |

## コードとテストで確認した点

- 初回の送信前に、認証トークンを除いた送信内容を複製し、作成キー・送信内容のハッシュ・下書きのハッシュを保存する。照会が `missing` なら元の投稿者として、保存済みの送信内容と同じキーで再送する。変更した下書きがある場合は再送前に確認する。実装は `packages/frontend/src/utility/multi-note.ts` の `startNoteCreate` と `MkPostForm.vue` の `recoverPendingResult`。
- 初回にサーバーから構造化された利用者エラーか権限エラーが返り、実際のHTTPステータスが4xxで、投稿者本人の照会が `missing` の場合だけ、キーの解除を試みる。同時に別のタブが再送を開始していればキーを保持する。実装は `misskey-api.ts` の `getApiErrorStatus` と `MkPostForm.vue` の `releaseRejectedCreate`。
- 下書き全体への書き込みは `withDraftLock` を通る。Web Locks が使えない場合は IndexedDB の読み書きトランザクションを使用する。予約と確定では、ロックを取得できた場合だけ処理を進める。`finishPendingDraft` は最新の下書きのキーと版を検査して、送信時の版だけを削除する。他のタブが編集した版には本文を残す。
- 通常の投稿フォームでは、明示した宛先を同期的に記録し、機能が停止しても選択を表示する。ローカル下書きからの復元は、チャンネルの有無と通常投稿先の指定を両方読む。

## 再レビューで見つかった境界条件

1. 通常投稿先を外しチャンネルが0件の状態でも、予約投稿のメニューやURLからの引用を選べた。予約日時または引用先を設定すると投稿先の検査が外れ、通常投稿を送れる状態になった。
2. 元の送信内容を再送して応答を待つ間も本文を編集できた。再送の直前に取った下書きのハッシュで確定処理を行うため、その後に同じタブで書いた本文がフォームから消える場合があった。初回も送信内容を組み立ててから作成キーを予約するまでに非同期処理がある。

1件目の修正では、通常投稿先がオフなら、チャンネルが0件でも明示的に選んだ宛先として扱う。予定登録とURLからの引用では、この状態からモードを切り替えない。すでに開いていた予定登録メニューから呼び出した場合にも、実行時に再度検査する。この修正の確認中に、従来の公開チャンネルへの返信・引用まで送れなくなる初期化条件を見つけ、実装担当に戻した。

2件目の修正では、最初の送信内容を作る時点で下書きの内容も複製し、非同期プラグインの終了後とロック内の予約時に照合する。結果確認中は本文欄を無効にする。再送成功後に現在の下書きのハッシュを取り直し、追記が届いていれば編集画面と下書きを保持する。

従来のチャンネル返信・引用は、初期表示とリセットの両方で固定の宛先を引き継ぐ。ResoLove と GridSpace の両方で `initiallyPlaced` の条件を確認した。フォームのテストでは、返信が `channelId` と `replyId`、引用が `channelId` と `renoteId` を送ることを確認している。

## 判定

今回対象の3件と、再レビュー中に見つかった境界条件はいずれも修正を確認した。実装担当による近接テストの最終結果は8スイート50件成功。レビューでは [投稿フォームのテスト](../packages/frontend/test/unit/multi-note-composer.test.ts) の操作と期待値を確認した。2つのフォームによる同時予約の試験は同じストレージと模擬ロックを使う。実際のブラウザーの複数タブでの動作は、統合側の受け入れ試験で扱う。

### 専用返信ヘッダーの追確認

実ブラウザーで、公開の専用返信が「フォロワー」と表示される問題が見つかった。両フォークの `MkGridspacePostForm.vue` で、返信の公開範囲は投稿準備APIの応答が届いてから表示することを確認した。`public` は地球、`followers` は鍵、`specified` は封筒のアイコンと、それぞれに対応する公開範囲名を使う。固定チャンネルのフォームは従来どおりチャンネル名を表示する。3種類の表示とアイコンは [返信フォームのテスト](../packages/frontend/test/unit/gridspace-channel-composer.test.ts) でも検証している。この修正に対する追加指摘はない。
