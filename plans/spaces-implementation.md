## 2. 全体の構成

```
ブラウザ ──(1) API と ストリーミング──▶ Misskey(自宅の VM。いまのまま)
   │                                      │
   │                                      └─(3) 部屋を消す、人を外す ──▶ LiveKit
   └──(2) 音声と画面共有 ───────────────────────────────────────────▶ LiveKit(VPS)
```

- (1) スペースを開く、入る、いる人の一覧、チャット、設定の変更。すべて Misskey が受ける。
- (2) 音声と画面共有。ブラウザと LiveKit が直接やり取りする。Misskey も自宅の回線も通らない。
- (3) Misskey から LiveKit への操作。スペースを閉じたときに部屋を消すことと、追い出した人を外すことだけ。インターネット越しに HTTPS で呼ぶ。

役割の分け方は次のとおり。

- **だれがいるか**は Misskey が持つ。入った人は全員 LiveKit につなぐ(2026-11-26 変更)が、LiveKit が止まってもいる人とチャットを動かし続けるため、LiveKit の参加者一覧には頼らない。
- **だれが話しているか、マイクが入っているか**は LiveKit のクライアントから直接取る。Misskey は関わらない。
- LiveKit から Misskey への通知(Webhook)は使わない。
- LiveKit が止まっても、Misskey 側(いる人、チャット)は動き続ける。通話画面には「通話につながりません」と出す。

## 3. LiveKit の置き方

LiveKit は VPS に置く(2026-11-26 決定)。Misskey と同じホストに置く案は 3.5 の理由でやめた。

2026-11-26 に VPS へのデプロイが済み、`wss://livekit.grid-space.io` で動いている。確認できたことと残っていることは 3.6 に書く。IP、API キー、起動・更新・再起動の手順は、別リポジトリ `home-server-docs` の `configs/gridspace-livekit/README.md` にある。この文書には写さない。

### 3.1 VPS

LiveKit は、ほかのサービスがすでに動いている既存の VPS に同居させた。TLS は、その VPS にもともとある Nginx が受け持つ(証明書は Certbot で取り、自動で更新する)。Misskey のデータは置かない。

LiveKit のバージョンは v1.13.11。Docker Compose で動かし、イメージはタグと digest の両方で固定している。

| ポート | 種類 | 用途 |
| --- | --- | --- |
| 443 | TCP | 接続の開始と操作(WebSocket)。Nginx が TLS を終えて、LiveKit の 7880 に渡す |
| 80 | TCP | TLS 証明書の取得 |
| 7881 | TCP | UDP が通らない人の予備 |
| 7882 | UDP | 音声と画面共有の本体 |

- UDP は 1 ポートにまとめる(`rtc.udp_port: 7882`)。既定の 50000〜60000 を開けるより、ファイアウォールの設定が1行で済む。
- 7880 は外に開けない。`127.0.0.1` だけで待ち受け、VPS の中の Nginx からだけ届く。
- LiveKit 用の Redis は要らない(1台構成のため)。

LiveKit の設定ファイルの骨子。

```yaml
port: 7880
rtc:
  tcp_port: 7881
  udp_port: 7882
  use_external_ip: true
keys:
  # キーと秘密は環境変数から入れる。このファイルには書かない
```

VPS を選ぶときに見る点。いまの VPS がこの目安に合うかは確かめていない(3.6)。

| 点 | 目安 | 理由 |
| --- | --- | --- |
| 場所 | 日本国内 | 遅延に直接効く |
| 大きさ | 1 vCPU、メモリ 1 GiB から | 30人ほどの音声なら足りる見込み。測ってはいない |
| 通信量の上限 | 月の転送量が多いもの、または無制限 | 画面共有を使うと通信量が増える。先に効くのはここ |

### 3.2 DNS

`livekit.grid-space.io` を VPS の IP に直接向ける。Cloudflare のプロキシ(オレンジの雲)は通さない。通すと UDP が届かない。

自宅側の構成(Cloudflare Tunnel、ルーター)には手を入れない。

### 3.3 Misskey 側の設定

`.config/default.yml` に `spaces` の節を足す。無ければ機能ごと無効にする。

```yaml
spaces:
  enabled: true
  livekit:
    url: wss://livekit.grid-space.io     # ブラウザがつなぐ先。Misskey からの操作も同じホストに HTTPS で送る
    apiKey: ...
    apiSecretEnv: SPACES_LIVEKIT_SECRET  # 秘密は環境変数に置く
```

- キーと秘密は、VPS の LiveKit と自宅の Misskey の両方に同じものを置く。トークンは Misskey が手元で署名するので、発行のたびに VPS へ問い合わせることはない。
- 秘密はいま VPS にだけある。自宅の Misskey にはまだ置いていない。本番に出すとき(10章の順7)に環境変数 `SPACES_LIVEKIT_SECRET` として置く。
- 秘密を環境変数の名前で指す形は、既存の `gridspace` の節と同じ考え方にする。
- `packages/backend/src/config.ts` に型と読み込みを足す。`.config/example.yml` に説明つきの例を足す。
- フロントには `meta` で「スペースが有効か」だけを渡す。LiveKit の URL はトークンと一緒に渡す(5.2)。

### 3.4 手元で動かすとき

開発では、手元の compose に LiveKit を1つ足して動かす。LiveKit の開発用の起動方法(固定のキーで立ち上がる)を使い、`url` を `ws://localhost:7880` にする。VPS は要らない。

### 3.5 同じホストに置く案をやめた理由

インフラの文書(別リポジトリ `home-server-docs`)を 2026-11-26 に調べた結果による。実機は見ていない。

- 本番は自宅の VM で、外からの経路は Cloudflare Tunnel。Tunnel は HTTP 用で、音声の本体(UDP)を通せない。自宅のルーターに、VM へ直接届く入口を2つ開ける必要がある。
- VM は 2 vCPU、メモリ 3 GiB で、Misskey、PostgreSQL、Redis が同居している。
- 物理ホストの NIC に通信が止まった履歴がある(2026-11-14)。

### 3.6 確かめたこと、まだ確かめていないこと

2026-11-26 のデプロイで確かめたこと(デプロイの記録による。この文書を書く側では試していない)。

- 2つのクライアントが `wss://livekit.grid-space.io` につながり、合成した音を送って受け取れた。
- 音声は UDP 7882 を通った。TCP 7881 への切り替えは起きなかった。
- 7880 は外から届かない。
- TLS 証明書の自動更新の試験(dry-run と Nginx の再読み込み)が通った。

まだ確かめていないこと。

- 実際のマイクで人が話して聞く通話。
- 画面共有を数人が同時に見たときの CPU の負荷と通信量。30人規模の負荷も測っていない。VPS はほかのサービスと同居しているので、そちらへの影響も見る。段階2の最初に測る。

## 4. データ

### 4.1 テーブル `space`(新規)

エンティティは `packages/backend/src/models/Space.ts` の `MiSpace`。作った時刻は ID から取る(既存のテーブルと同じ)。

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | id | |
| `hostId` | id、索引あり、ユーザー削除で一緒に消す | ホスト |
| `name` | varchar(128) | なまえ |
| ~~`voice`~~ | — | 作らない。通話の無いスペースはやめた(2026-11-26 変更) |
| `access` | enum `local` / `followers` | 入れる人 |

| `announceNoteId` | id、null あり | お知らせノート |
| `summaryNoteId` | id、null あり | まとめノート(段階2) |
| `participantIds` | id の配列 | 一度でも入った人。まとめに使う |
| `peakCount` | integer | 同時にいた人数の最大 |

- 開いているスペースの一覧は `endedAt IS NULL` で引く。
- 「みんながタイルを置ける」「はじめの状態」の列は段階3で足す。段階1の「ひらく」画面にはこの2項目を出さない。

migration は新規ファイル1つ。`up()` と `down()` の両方を書き、`pnpm --filter backend check-migrations` を通す。

### 4.2 Redis(いる人とチャット)

閉じれば要らなくなる情報は DB に入れない。読み書きは `SpaceService` にまとめる。Redis でいる人を管理する既存の例に `AvatarWalkService` があるが、合わせる必要はない。新しく書いてよい。

| キー | 型 | 内容 |
| --- | --- | --- |
| `space:{id}:members` | hash | ユーザー ID → 入った時刻、入り方(しゃべる / 聞くだけ)、ユーザーの表示情報 |
| `space:{id}:sessions` | hash | ユーザー ID → 有効な接続の ID |
| `space:{id}:active` | sorted set | ユーザー ID → 最後に生存確認が来た時刻 |
| `space:{id}:messages` | list | チャットの直近200件 |
| `space:{id}:emptySince` | string | だれもいなくなった時刻 |
| `space:{id}:kicked` | set | 追い出された人のユーザー ID(5.4) |

- ブラウザは 5 秒ごとに生存確認を送る。90 秒来なければ、その人は出たものとして扱う(どちらも仮の値)。
- Misskey を再起動しても Redis の中身は残る。ブラウザがつなぎ直せば元どおりになる。

### 4.3 ノートのテーブルは変えない

お知らせノートは、本文にスペースの URL が入った普通のノートにする(8)。`note` に列を足す案は採らなかった。理由は次の3つ。

- ノートを返す処理すべてに手が入り、`misskey-js` の型の作り直しも要る。
- URL から描く方式なら、だれかがスペースの URL を貼っただけのノートにもカードが出る。
- 試作を早く回すという方針に合う。

## 5. API

エンドポイントは `packages/backend/src/server/api/endpoints/spaces/` に置く。追加したら `endpoint-list.ts` に登録し、`pnpm build-misskey-js-with-types` で型を作り直す。権限の種類として `read:spaces` と `write:spaces` を足す(`packages/misskey-js/src/consts.ts` の一覧にも足す)。

### 5.1 一覧

| エンドポイント | できる人 | すること |
| --- | --- | --- |
| `spaces/create` | ログインユーザー全員 | スペースを作る。お知らせノートを出す。作ったスペースを返す |
| `spaces/show` | ログインユーザー | 1つ返す。入れない人にも、名前・ホスト・人数・入れるかどうかは返す |
| `spaces/list` | ログインユーザー | 開いていて自分が入れるスペースを返す。タイムラインの入口が使う |
| `spaces/token` | 入れる人 | LiveKit のトークンと URL を返す |
| `spaces/update` | ホスト | 名前と「入れる人」を変える |
| `spaces/end` | ホスト | 閉じる |
| `spaces/mute` | ホスト | 指定した人のマイクを切らせる |
| `spaces/kick` | ホスト | 指定した人を追い出す |

入る・出る・チャットはエンドポイントにせず、ストリーミングで行う(6)。

返す形は `Space` として `json-schema.ts` に登録する。中身は `space` の列に、ホストの表示情報、いまの人数、`canJoin`(自分が入れるか)を足したもの。

### 5.2 `spaces/token`

- 入れるかを判定し(5.3)、閉じていないことと、本人がスペースに入っている(ストリーミングでつないでいる)ことを確かめてから発行する。
- トークンの中身: 部屋の名前はスペースの ID、本人の識別子はユーザー ID、有効期限は 10 分。
- 権限は全員同じにする。マイクと画面共有を出せる、受け取れる。「だれでも話せる」と決めたので、聞くだけの人も同じトークンでマイクを切っているだけにする。
- 出せる種類は `microphone`、`screen_share`、`screen_share_audio` に限る。カメラは入れない。
- LiveKit は書かなかった権限を「許可」として扱う。禁止したいものは必ず false と書く。
- 有効期限が切れてつなぎ直せなくなったら、ブラウザがもう一度このエンドポイントを呼ぶ。
- 発行には `livekit-server-sdk` を使う。backend の依存に足す。

### 5.3 入れるかの判定

`SpaceService.canJoin(user, space)` の1か所にまとめ、`spaces/show`、`spaces/list`、`spaces/token`、ストリーミングの接続のすべてがこれを呼ぶ。

1. 閉じていたら入れない。
2. ホスト本人は入れる。
3. ホストとブロックの関係がどちら向きかにあれば入れない。このスペースから追い出された人も入れない(5.4)。
4. `access` が `local` なら入れる。ログインユーザーはこのサーバーの人だけなので、追加の確認は要らない。
5. `access` が `followers` なら、ホストをフォローしている人だけ入れる。

### 5.4 ホストのミュートと追い出し

計画で「ホストは個別にミュートや追い出しができる」と決めてある。

- **ミュート**: 相手の画面に `muted` を送り、相手のブラウザがマイクを切る。本人はもう一度マイクを入れられる。話す権限そのものは取り上げない(仮)。
- **追い出し**: Redis の `space:{id}:kicked` にユーザー ID を足し、相手に `kicked` を送って接続を切る。LiveKit からもその人を外す。5.3 の判定はこの一覧を見て、同じスペースには入り直せないようにする。スペースが閉じれば一覧も消える。

### 5.5 作るときの制限

- 1人が同時に開けるスペースは1つ。開いているものがあれば `spaces/create` はエラーを返す。
- 回数の制限は 1 時間に 10 回。人数や時間の上限は設けない(計画の決定どおり)。

## 6. ストリーミング

チャンネル `space` を足す。置き場所は `packages/backend/src/server/api/stream/channels/space.ts`。登録先は `Connection.ts` と `ServerModule.ts`、型は `GlobalEventService.ts` と `packages/misskey-js/src/streaming.types.ts`。

**このチャンネルにつないでいる間が「スペースにいる」**。つなぐと入り、切ると出る。

### 6.1 つなぐとき

引数は `spaceId` と入り方(`voice` = しゃべる / `listen` = 聞くだけ)。

1. 5.3 の判定をする。入れなければ接続を断る。
2. Redis の「いる人」に足す。`space.participantIds` と `peakCount` を更新する。
3. つないだ本人に `snapshot` を送る。中身はスペース、いる人の一覧、チャットの直近200件。
4. ほかの人に `joined` を送る。

### 6.2 サーバーから届くもの

| 名前 | 中身 | いつ |
| --- | --- | --- |
| `snapshot` | スペース、いる人、チャット | つないだ直後 |
| `joined` | 入った人 | だれかが入った |
| `left` | ユーザー ID | だれかが出た |
| `memberUpdated` | ユーザー ID、入り方 | 入り方を変えた |
| `message` | チャット1件 | だれかが書いた |
| `updated` | スペース | ホストが設定を変えた |
| `ended` | なし | 閉じた |
| `replaced` | なし | 同じ人が別の画面で入った |
| `muted` | なし | ホストにマイクを切られた(本人にだけ届く) |
| `kicked` | なし | ホストに追い出された(本人にだけ届く) |

### 6.3 ブラウザから送るもの

| 名前 | 中身 | すること |
| --- | --- | --- |
| `heartbeat` | なし | 生存確認の時刻を更新する |
| `setMode` | 入り方 | 入り方を変え、`memberUpdated` を配る |
| `say` | 本文(2000字まで) | チャットに足し、`message` を配る |

### 6.4 段階3以降のための境界

タイルやアイテムの状態(`space.shared` など)は、このチャンネルに種類を足して流す。段階1ではその種類を作らないが、チャンネルの名前と「つないでいる間がいる状態」という約束は変えない。

位置のように数が多い情報は、あとで LiveKit のデータ通信に移す(計画 5.6)。そのため、トークンのデータ送信の権限は段階1から許可しておく。

## 7. 開いてから閉じるまで

| 出来事 | 起きること |
| --- | --- |
| ひらく | `space` に1行足す。お知らせノートを出す(範囲が「出さない」以外)。LiveKit の部屋は、最初の人がつないだときに LiveKit が自動で作る |
| ホストの回線が切れる | 何もしない。開いたまま |
| 全員が出る | `emptySince` に時刻を書く。だれかが入れば消す |
| 30分だれもいない | 自動で閉じる。定期ジョブが 5 分ごとに調べる |
| 閉じる(ホスト、または自動) | `endedAt` を書く。`ended` を配る。LiveKit の部屋を消す(つながっている人は切れる)。Redis のキーを消す。まとめノートを出す(段階2) |

- 定期ジョブは system キューに足す。既存の `CheckExpiredMutingsProcessorService` と同じ形にする。
- 閉じる処理は `SpaceService.end()` の1か所にまとめ、ホストの操作と定期ジョブの両方がこれを呼ぶ。
- 閉じたスペースの URL を開くと、まとめの画面になる。

## 8. ノートとカード

### 8.1 お知らせノート

`spaces/create` の中で `NoteCreateService` を使って出す。

| スペースの設定 | ノートの設定 |
| --- | --- |
| 範囲が「このサーバーだけ」 | `localOnly: true` |
| 範囲が「ふつうのノート」 | `localOnly: false` |
| 範囲が「出さない」 | ノートを出さない |
| 入れる人が「フォロワーだけ」 | 公開範囲を「フォロワー」にする |
| 入れる人が「サーバーの全員」 | 公開範囲を「パブリック」にする |

本文は「スペースの名前」と「スペースの URL」の2行。

ほかのサーバーに届いた場合は、URL つきの普通のノートとして見える。リンクを開くとこのサーバーのログイン画面になる。計画の宿題にあった「他サーバーでの見え方」は、これを答えとする。

### 8.2 カード

`MkNote.vue` は本文の URL を `MkUrlPreview` で描いている。ここで、自分のサーバーの `/spaces/{id}` の形をした URL だけを `MkSpaceCard` に差し替える。

- カードは `spaces/show` を呼んで、名前、ホスト、いまの人数、開いているか閉じたかを出す。
- 同じスペースを何度も問い合わせないよう、フロントで ID ごとに 30 秒覚えておく。
- 閉じたスペースのカードは、まとめ(人数と時間)の表示になる。

### 8.3 まとめノート(段階2)

## 12. 段階1を実装した結果(2026-11-26)

段階1(10章の順1〜6)を実装した。設計と違う形にしたところと、確かめた範囲をここに書く。

### 12.1 設計と違うところ

| 設計 | 実装 | 理由 |
| --- | --- | --- |
| `MkSpaceJoin`、`MkSpaceCall`、`MkSpaceSummary` を別のコンポーネントにする(9.1) | 3つとも `pages/space.vue` の中に書いた | ほかの画面から使わないため |
| `MkSpaceOpenDialog` を作る(9.1) | 既存の入力ダイアログ(`os.form`)を使った。入口は `utility/space.ts` の `openSpaceCreateDialog` | 入力が4項目で、専用の画面が要らないため |
| ひらく入口の場所は決めていなかった | 一覧のページ `/spaces` を足し、そこに「スペースをひらく」を置いた。ナビゲーションの項目もここへ行く | |
| `spaces/token` は「入れる人」が呼べる(5.1) | 権限の種類を `write:spaces` にした。チャットの発言も `write:spaces` を持つアプリだけ | マイクを出せるトークンを、見るだけの権限のアプリに渡さないため |
| 1人1つの制限は `spaces/create` で調べる(5.5) | それに加えて、DB に「開いているスペースはホストごとに1つ」の一意索引を置いた | 同時に2回呼ばれると、調べるだけでは防げないため |
| Redis のキーに `sessions` がある(4.2) | 接続の ID は `members` の値の中に持たせた。`sessions` は作っていない | 読み書きが1回で済むため |
| 手元の LiveKit は「手元の compose に足す」(3.4) | 別ファイル `compose.spaces-dev.yml` にした | DB だけ使う人にまで LiveKit を取得させないため |

### 12.2 設計に無く、足したもの

- **通話にいる人の突き合わせ**。LiveKit は発行済みのトークンを取り消せない。追い出された人が手元のトークンでつなぎ直す、またはトークンだけ取って一覧に載らずに聞く、という抜け道がある。これを止めるため、だれかの生存確認のたびに(実際に調べるのは20秒に1回)、LiveKit にいるのに「いる人」に入っていない人を外す。追い出された人は見つけしだい外す。それ以外の人は、入っている途中の人を誤って外さないよう、2回続けて見つけてから外す。そのため、追い出された人は最長で20秒ほど、一覧に載らずに聞く人は最長で40秒ほど通話にいられる。
- **音声の再生が止められたときのボタン**。ブラウザが音を鳴らすのを止めた場合、通話画面に「音声を再生」を出す。
- **通話につなぐ順番**。通話(LiveKit)には、スペースに入れたことが分かってからつなぐ。入る前につなぐと、上の突き合わせに外されるおそれがあるため。
- **つなぎ直しの見張り**。ストリーミングがつなぎ直されたあと、10秒たっても入り直せなければ、スペースから出たものとして扱う。

### 12.3 まだ残っている弱いところ

- スペースを閉じたあとも、発行から10分以内のトークンを持つ人は LiveKit の部屋を作り直せる。閉じたあとは突き合わせが動かないため。LiveKit 側で「部屋を自動で作らない」設定にすれば止まるが、VPS の設定の変更が要る。
- 生存確認が途絶えた人を外す処理と、その人の生存確認が同時に来ると、いる人から外れることがある。次につなぎ直すまで一覧に出ない。
- LiveKit への操作(部屋を消す、人を外す)が失敗しても、やり直さない。記録に残すだけ。

### 12.4 確かめた範囲

手元の環境(LiveKit は `compose.spaces-dev.yml`、Misskey は別の DB と別のポート)で確かめた。本番の VPS の LiveKit にはつないでいない。

| 確かめたこと | 方法 | 結果 |
| --- | --- | --- |
| 設定の検査、入れるかの判定、自動で閉じる判定 | 単体テスト 22 件 | 通過 |
| 作る、見る、一覧、トークン、変える、ミュート、追い出し、閉じる、置き換え、フォロワーだけ | 動いているサーバーに API とストリーミングで通しの確認 34 項目 | 通過 |
| 2つのブラウザで入る、音声の受信、マイクの入り切りの表示、チャット、ページを移っても続く、閉じる | ブラウザ2つを自動で操作。マイクは偽のもの | 19 項目中 18 通過 |
| migration | 適用、巻き戻し、再適用、`check-migrations` | 通過 |

確かめられていないこと。

- **話している人の縁取り**。偽のマイクの音がブラウザの雑音除去で消え、無音として届いたため、確かめられなかった。実際のマイクで見る必要がある。
- 実際のマイクとスピーカーで、人が話して聞くこと。
- スマホのブラウザ。
- 通話にいる人の突き合わせが、実際に人を外すところ(外す処理は書いたが、抜け道を使う側を作って試してはいない)。
- 30分たって自動で閉じるところを、実際のジョブで待つこと(判定は単体テストで見た)。

### 12.5 入り方の変更(2026-11-26)

実際に触ってみての変更。

- 「通話あり」の選択をやめた。スペースには必ず通話がある。`space` の `voice` の列、`spaces/create` の `voice` の引数は無くした。
- 入り方は「聞くだけ」と「しゃべる」の2つにした。「文字だけ」はやめた。入った人は全員 LiveKit につなぐ。
- かわりに「スピーカーを切る」を足した。通話にはつないだまま、自分の画面で鳴らす音だけを止める。サーバーには送らず、ほかの人の画面にも出さない。
- 入った人が全員 LiveKit につなぐようになったので、`spaces/token` は「スペースに入っている人」にだけ出すようにした。入らずにトークンだけ取って聞く抜け道を、発行の時点で止める。
- 確かめた範囲は、API とストリーミングの通しが 35 項目すべて通過、ブラウザ2つの通しが 21 項目中 20 通過(残りは 12.4 と同じく、話している人の縁取り)。
