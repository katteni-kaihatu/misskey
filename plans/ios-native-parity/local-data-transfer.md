# S1-4 ローカルデータの移行

2026-11-15〜16の部分実装。S1全体の受入完了ではない。Webコードは実サーバーへ未配布。隔離した合成PWAでは、新しい移行画面をiPhoneで操作し、Filesの取込み・保存・再選択と回収ファイルのバイト一致を確認した。障害・復旧・全保存状態は別に検証する。

## 利用する経路

設定の「プロファイル管理」から「ローカルデータの移行」を開く。書き出す内容を確認してファイルへ保存し、同じorigin・同じユーザーでログインした移行先から選ぶ。取り込み前に件数、データの種類、既存値の変更件数を表示する。識別子は任意に開いて確認でき、200件単位で全件を見られる。移行先のデータを書き出す操作も用意した。

取り込みには、ファイルの提供元とCSS・プラグイン・スクリプト設定を信頼する明示操作と、最後の確認を要する。ファイルを読んだだけでは設定を適用しない。Safariの保存領域をネイティブから読み出さず、WebのFile入力・Blobダウンロードを使う。iOS側は既存のFiles選択・WKDownloadアダプターを利用する想定で、新しい認証ブリッジ操作は公開しない。

## 対象と除外

| 保存先 | 対象 |
|---|---|
| localStorage | 設定プロファイル、投稿・チャット下書き、Scratchpad、表示設定、テーマ/CSS、AiScript、UI状態・既読位置の既存名前空間 |
| `keyval-store/keyval` | base/deckのPizzax状態・registry cache、旧AvatarWalk保存値 |
| `MisskeyAvatarWalk/atlas` | AvatarWalkの画像・保存値。BlobのMIMEとバイト列を保持 |
| 旧保存方式 | `idbfallback::`およびlocalStorage上のPizzax値を対応するIndexedDBレコードへまとめる。同じキーのIndexedDB値があればそちらを採用 |

対象名前空間の未知フィールド、設定のscope/value/meta、将来キー、画像以外の構造化値を保持する。移行先にしかない下書きのキー・設定範囲・状態フィールドも残す。同じキー・範囲の値は確認後に取り込み元で置き換える。

アプリが管理する`account`、旧`accounts`トークン一覧、`accountTokens`、`pluginTokens`、`accountInfos`、通常キャッシュ、移行journal/使用済みIDは書き出さない。取り込み時にも同じ制限を検査する。移行先の認証用フィールドは既存のものを保持し、journalにも複製しない。未分類のトップレベル保存先を推測で移さない。

ユーザーが書いた下書き・スクリプト・保存値には別の秘密情報が含まれ得るため、ファイルを他人へ共有しない旨を表示する。任意のユーザーデータから秘密値を自動で見分けることは保証しない。

## ファイルの契約

拡張子は`.gridspace-localdata`、MIMEは`application/vnd.gridspace.local-data`。資格情報や画像をJSONのbase64列へ変換しない。

1. 8 bytesのASCIIマジック`GSLOCAL1`。
2. manifestのUTF-8バイト数をbig-endian UInt32で保存。
3. JSON manifest。schema、root参照、構造化グラフのnodes、後続バイナリ各partのサイズ。
4. 宣言した順番のバイナリpart。切詰め・余分な末尾・範囲外参照・未対応schemaを拒否。

全体512 MiB、manifest 16 MiB、グラフ100,000ノード/エントリー、構造の深さ200、保存レコード10,000件を上限にする。Blob/File、ArrayBufferと同じArrayBufferを参照するtyped view、Date、Map/Set、循環・共有参照、undefined、BigInt、非有限数を扱う。SharedArrayBufferや関数など未対応値は明示的に拒否し、消して成功扱いにしない。既存ストアが通常objectへcloneする値の`__proto__`キーも適用前に拒否する。

ファイル外枠の中のsnapshotはformat/version/id/createdAt/source/recordsを持つ。sourceはorigin/userId/webVersionのみ。IDはUUID、取り込み先で成功したIDを記録し、同じ保存領域への再適用を拒否する。ログアウトでこの記録も削除するため、保存領域の初期化をまたぐ全世界共通の一回限りを保証するものではない。

## 変更・中断・認証

- 確認画面を作る時点の値と、適用前・適用後の値を照合する。fingerprintはバイナリを含む全バイトを4 MiB以下のチャンクで検査し、一度に巨大なArrayBufferへまとめない。
- 取り込んだBlobは4 MiB以下ずつ読み、元ファイルの範囲参照から独立させて保持する。WebKitのネイティブ書出しで、範囲の代わりに元ファイル全体が混入する問題を回避するため。バイナリ全体のコピーは発生し、512 MiB上限付近での実機メモリ余裕は未確認。
- `GridSpaceLocalTransfer`のjournalへ認証情報を除いた変更前後の値を保存してから書く。使用済みIDとcommit状態は同じIndexedDB transactionで確定する。
- `_boot_.ts`はjournalの復旧を待ってからmain/sub bootをdynamic importする。未commitの変更を戻す前に、設定・Pizzax・プラグインを初期化しない。通常起動で復旧markerがなければIndexedDBへ触れない。
- Web Locksで移行とWebのアカウント変更を直列化する。同じdocumentの変更意図は即時に取り込みを中断し、他のdocumentへは資格情報を含まない取消ヒントを送る。復元後に切替・ログアウトを進める。古いWeb環境では既存のログイン動作を保ち、ロックを使えない取り込みは拒否する。
- ログアウトでは新しいjournal DBも削除対象にする。設定の自動バックアップやネイティブ失効通知の失敗を理由にWeb資格情報を残さない。
- 別の画面が書いた値へ自動復元を上書きしない。判別できない場合はjournalを残し、通常起動前の専用画面で「現在の値を残す／移行前の値に戻す」を選ぶ。値のプレビューはテキストとして最大8,000文字まで表示し、CSS・スクリプトを実行せず、バイナリ本体も描画しない。一覧は100件単位。通常成功時の再読み込みは取り込んだdocumentだけに限定し、他の窓で待機する認証操作を中断しない。

## 復旧競合の確認と退避

専用画面はVueとi18nだけで表示し、アプリの設定・Pizzax・UGC・通常の画面を起動する前に確認を待つ。選択の初期値は「現在の値を残す」。ログイン状態が移行時と違う場合は以前の内容を表示せず、元の値への復元も許可しない。現在の値を残して起動し、必要ならその後に元のアカウントへログインできる。

確認後にidentity・journalのバージョン・各現在値のfingerprintを再照合し、変化していたら保存せず選択し直す。元のjournalの退避と、利用者の選択を表す`recovering` journalへの置換は、一つのIndexedDB transactionで行う。 WebKitで保存済みBlobの参照先を失わないよう、置換前に4 MiB以下ずつ読んで独立したBlobへコピーする。コピー中は書込みtransactionを開かず、transaction内でjournalのバージョンを再照合する。選択を反映する途中で中断しても、次回起動でその値への復旧を再開する。再び別の変更と競合すれば、もう一度専用画面を表示する。元から壊れていた保存値も復元記録ではそのまま保持するが、通常の移行snapshotとしての検証は緩めない。

退避記録は「プロファイル管理」から同じorigin・ユーザーのものだけを一覧・保存・確認付き削除できる。拡張子`.gridspace-recovery`の調査用archiveで、通常の移行ファイルとして取り込めない。元の変更前後の値と、同じアカウントで確認した現在値をバイナリのまま保存する。アカウントが異なる場合は現在値を以前のアカウントの記録へ複製しない。アプリ管理の認証フィールドは除外する。通常の一覧取得はmetadataキーだけを読み、大きなBlob本体を読み込まない。ログアウト・保存領域の削除で退避も消えるため、必要な記録を先に保存する旨を表示する。

壊れたjournalや利用できない保存機能に対しては、証拠を消す操作を推測で提供せず、記録を保持した再試行画面に留まる。 IndexedDBの書込み・完了・退避のコールバック内で同期的な保存拒否が起きた場合も、transactionを明示的に取り消し、起動全体の失敗画面へ例外を漏らさない。Webの保存領域内のユーザーIDは、ネイティブAPIの認証証明には利用しない。

## 検証と残件

共通codec/方針/復旧、未知の設定の後続commit、認証保存の境界をunit testで確認。実ブラウザでは実際のIndexedDB・Blob・Web Locks、64 MiB画像、認証情報の保持、取消・quota相当の失敗・再起動を確認。PWAのe2eでは新規パスワードログイン→書き出し→確認→取り込み→再読み込み、再適用拒否、boot前のjournal復旧を確認する。結果の数と証拠は[検証記録](validation.md)へ記載する。

追加のiPhone比較では、USBの開発用IPv6トンネル経由で新しいWebを開き、新規ログイン、Files取込み、信頼確認・適用、再起動、書出し、Files保存、再起動後の保存コピー再選択まで成功した。回収した原本と保存コピーの4レコード・未知フィールド・2 MiB Blob全バイトも一致した。IPv6 Blob URLのSwift/CFURLでの表現差を共通origin判定で補正し、encoded hostや別originは拒否する。

起動前復旧は、Scratchpadの合成値で自動rollback、競合の現在値保持/移行前への復元、異なるアカウントの値・復元記録の非表示をSimulatorと実機で比較した。通常のeditorを起動する前に確認を待ち、タグを含む値を文字列のまま表示し、選択後・再起動後の値とidentityが一致した。自分の退避記録の表示・削除取消・確認付き削除も実機で成功した。

Blobを含む競合復旧もSimulatorと実機で成功した。移行前・取込み値・競合した現在値の3種類の2 MiB Blobを含む退避記録と、復元後の通常snapshotをFilesへ保存・回収し、全バイト・MIME・未知metadata・identity・hashを比較した。再起動後に保存した退避記録を選び、通常の移行として取り込めないことも確認した。

壊れたjournal、journal DBへのアクセス拒否、退避作成途中の保存拒否は、ChromiumとWebKitのPWA UIで比較した。記録・現在値・pending marker・アカウントIDを保持し、壊れた記録では認証boot APIも呼ばない。外部で記録/保存条件を修正した後の再試行で復旧でき、途中の保存拒否では半端な退避記録を残さない。壊れた記録の保持・再試行・プロセス再起動と、外部で正しい記録へ修正した後の通常復旧は実機でも確認した。保存拒否は試験による例外注入であり、実機の空き容量を使い切った検証ではない。

次は実機の保存領域拒否/容量不足、選択・保存の取消と失敗、他の権限別fixture、容量不足・旧OS・複数窓の認証変更を比較する。通常の設定/Pizzax書込みをすべてrevision・共通ロックへ移したわけではなく、クラウドとの競合対処はS3の未完了項目。移行時はほかの窓を閉じる。今回の限定した復旧比較を全保存状態・全障害の段階合格として扱わない。
