## 0. 方向修正の要点（今回の変更）

ユーザーからの方向修正「デフォルト＋チャンネルってできるの」を受け、以下を確定した。

1. **「デフォルト」＝通常の投稿先（通常タイムライン）**。新規の通常投稿欄では「通常の投稿」を初期選択状態にする。
2. チャンネルを追加しても「通常の投稿」は自動解除しない。「通常の投稿＋複数チャンネル」も「チャンネルだけ」も選べる。どちらも原本は1件（本文/ID/会話/リアクション対象は共通）。
3. **投稿先は少なくとも1つ必要**（通常の投稿0件・チャンネル0件の同時成立は不可）。
4. チャンネル画面から開いた場合は既存互換でそのチャンネルのみ選択（「通常の投稿」は初期OFF）。利用者が後から「通常の投稿」を追加できる。
5. **チャンネル数の上限は設けない**（旧版の「最大5件」表示・文言・選択不可ロジックは撤去）。候補が多い場合も検索・選択済み表示で扱う。
6. 公開範囲は投稿全体に1つだけかかる。チャンネルを1件以上選ぶなら `public` が必須。現在値が home/followers/specified のときにチャンネルを選んでも**自動で変更しない**。利用者に切り替えを案内し、切り替えるまで送信不可にする。
7. チャンネルだけの投稿は既存互換で `localOnly=true`。通常の投稿も選んでいる場合は、既存の連合ON/OFF設定を尊重し、ONなら原本（通常の投稿として）は連合する。チャンネル掲載そのものは常にローカル。送信前に「どこへ流れるか」を明示する。
8. 公開範囲・原本URL・添付URLは既存の公開チャンネルと同じ扱いにする。掲載解除は一覧から外す操作で、投稿本体や添付を非公開にしない。全掲載失敗/解除後も未掲載であることと非公開であることを混同させない。

今回必須は掲載契約のM1〜M8、後回しはD1〜D5に従う。完全なURL失効、添付配信基盤の変更、本人限定の未掲載原本は今回のUI要件にしない。新方式の基本操作・既存閲覧制限・投稿結果不明時の復旧は実装する。

2026-11-21の要件更新により、Multi Noteの予約投稿と投稿後の掲載先追加・再追加は将来対応からも除外する。公開センシティブチャンネルも投稿先に選べる要件とし、必要なCWは投稿者が既存のCW欄で付ける。原本のCWを全掲載先で共用し、自動付与・入力必須化・掲載先別CW・センシティブ属性の混在による選択制御は追加しない。一律除外の撤去と投稿画面・チャンネル画面・デッキの対応は両リポジトリに実装済みで、実サーバーとブラウザで検証した。

これにより旧版にあった「投稿先0件＝通常投稿」という黙示の表現、ヘッダーのvisibilityボタンを複数選択時に隠す方針、「最大5件」という上限、遠隔候補の扱いの一部は本書で置き換える（差分は各節に記載）。

**要件に含めない操作**: 複製投稿、予約投稿との併用、投稿後の掲載先追加・再追加、返信/引用/Renoteをしながらの複数掲載、新しい非公開チャンネルの閲覧権限モデル。段階1のローカル限定という区分は当初の設計であり、連携先チャンネルの選択・掲載は段階2まで実装・検証済みとする。

2026-11-21の本番変更取り込みでは、既存の引用・リノート機能を新しいチャンネル投稿でも使えるようにする。閲覧中の掲載先を指定した参照から、通常投稿または一つのチャンネルへ引用・リノートできる。新規作成時に元の掲載先・共有設定・閲覧権限と投稿先の書込権限を確認し、複数の掲載先や通常投稿とチャンネルの同時指定は受け付けない。公開済み参照の表示は原本の現在の閲覧条件に従い、掲載解除だけでは原本URLを失効させない。詳細は[本番統合記録](../multi-note-production-integration.md)を参照する。

## 1. 目的

投稿欄から「投稿先」を複数選べるようにする。投稿先は **「通常の投稿」（通常タイムライン、既定でON）** と **チャンネル（0件以上、上限なし）** の組み合わせで、少なくとも1つ選ばれていれば任意の組み合わせが成立する。既存の単一チャンネル投稿・通常投稿の操作性を保ったまま、1つの本文・1つのURI・1つの会話・1つのリアクション対象を「通常の投稿」と複数チャンネルに同時掲載できる体験を提供する。

## 2. 段階1の画面設計

### 2.1 配置の方針

新しい「投稿先」行は、`MkPostFormHeader` が描画するヘッダー行とは**別の独立したブロック**として、ヘッダー直下・本文エリアの間に1本追加する（`MkPostFormHeader` のスロットの中には入れない）。既存の `targetChannel`（単一チャンネル）の仕組みを置き換えるのではなく、**「通常の投稿」フラグ＋チャンネルIDの配列**として一般化する。

- 投稿先の内訳は常に新しい投稿先行が一元的に表示する。ヘッダーの既存visibilityボタン（公開範囲: パブリック/ホーム/フォロワー/指定）は**チャンネル選択の有無に関わらず常に表示する**（旧版にあった「2件以上で非表示」という方針は撤回。公開範囲は投稿全体に1つだけかかる値であり、投稿先の組み合わせとは独立した概念として常設する）。
- 既定状態（新規の通常投稿欄を開いた直後）: 「通常の投稿」=ON、チャンネル=0件。投稿先行は「投稿先：通常の投稿」のチップ1つ＋「+ チャンネルを追加」ボタン。
- チャンネル画面から開いた場合（既存互換の入口）: 「通常の投稿」=OFF、選択済みチャンネル=そのチャンネルのみ。投稿先行はチャンネルチップ1つ＋「通常の投稿を追加」ボタン＋「+ チャンネルを追加」。
- 「通常の投稿」チップは**常設の固定チェック項目**で、投稿先行の最も左に置く。ON/OFFをその場でトグルできる（チップをタップで切替。シートを開かなくてもよい）。OFFにしようとした結果、チャンネルも0件になる場合はOFF操作を無効化し「投稿先が必要です」の理由を示す（送信不可の状態を作らせない）。
- チャンネルは0件〜任意件数。チップが並び、各チップに×ボタン。
- 新しい投稿先UIでは、チャンネルだけを選んだ場合もヘッダーの公開範囲ボタンを表示し、投稿全体の公開範囲を確認できるようにする。既存の `targetChannel != null` 分岐（`MkPostForm.vue:20-31`）は、新しい投稿先状態に合わせて変更する。旧APIによる単一チャンネル投稿の保存・配信互換は維持する。

### 2.2 投稿先行のUI要素

```
[投稿先ラベル] [✓ 通常の投稿] [チップ #A ×] [チップ #B ×] [+ チャンネルを追加]
通常の投稿と2件のチャンネルに掲載します。通常の投稿は連合します。チャンネル掲載はローカルのみです。
```

- 「通常の投稿」は常設の固定チェック項目（チェックボックス相当の見た目、ON時はアクセント色）。チャンネルチップと見た目を区別する（通常の投稿はチャンネルではないため、×で消すのではなくON/OFFトグルにする）。
- チャンネルのチップは「**提案**」の新規要素。既存の `.visibleUser`（`MkPostForm.vue:53-56`、`specified` 宛先のチップ）と同じ見た目パターン（丸背景・右に×ボタン）を転用する。発信元が複数ありうる段階2以降に備え、チップ内に発信元ラベルを小さく添える余白を最初から確保する（段階1は常にローカルなので表示は省略可）。
- `[+ チャンネルを追加]` ボタンは投稿先シートを開く。チャンネル選択済みがある場合は `[チャンネルを変更]` 表記にする。
- 状態文は送信先の内訳と連合の有無が一読でわかる文言にする（3.3節「送信前の明示」参照）。エラーではないので warn 色は使わない（投稿先0件・公開範囲衝突のときのみ warn/danger 色に切り替える）。

```
├──────────────────────────────────────────────────────┤
│ CW入力（任意）                                              │
│ ──────────────────────────────────────────            │
│ 本文テキストエリア                                            │
│ …                                                        │
├──────────────────────────────────────────────────────┤

```

公開範囲ボタンは投稿先の組み合わせに関わらず常時表示・常時操作可能（2.1節）。チャンネルを1件以上選んだ状態で公開範囲が `public` 以外の場合は、投稿先行の下にエラー状態文（「公開範囲をパブリックに切り替えてください」＋ワンタップで切替可能なボタン）を表示し、切り替えるまで投稿ボタンを無効化する（3.3節）。

### 2.4 モバイルワイヤーフレーム（投稿ダイアログ、通常の投稿＋チャンネル2件選択時）

```
┌──────────────────────────────┐
│ [戻る]            [🌐] [投稿]  │ ← 既存ヘッダー行（公開範囲ボタンは常に表示）
│ 投稿先 [✓通常] [#A ×] [#B ×] [変更] │ ← ×は常に表示、タップ領域44px以上
│ 通常の投稿と2件のチャンネルに掲載します。 │
│ 通常の投稿は連合します。          │
├──────────────────────────────┤
│ 本文                            │
│ …                              │
├──────────────────────────────┤
│ [添付][CW][絵文字]…(横スクロール)  │
└──────────────────────────────┘
```

- 狭い画面（`post-form.scss` の既存 `@container (max-width: 500px)` ブレークポイントを再利用。**既存**）でも、チップの×ボタンはデスクトップと同じく常時表示し、追加の確認ダイアログは出さない。誤タップ対策は「確認を挟む」のではなく「×のタップ領域を44×44px以上確保する」ことで行う。「通常の投稿」のON/OFFトグルも同様に44×44px以上のタップ領域を確保する。
- 投稿先ラベル・「通常の投稿」・チップが1行に収まらない場合は折り返す。投稿ボタンは常に右上に固定し隠れないようにする（既存の `.submit` margin 方針を維持）。

### 2.5 投稿先選択モーダル/シート

2026-11-21のチャンネル選択UI更新では、投稿欄内の選択欄を開くと、最初に両サイトのお気に入りを同じ一覧に表示する。ローカル・連携先を選ぶ切り替えは設けない。カテゴリは「お気に入り」「フォロー中」「トレンド」「検索」を既存のボタンとメニューで選び、検索欄も既存の入力部品に揃える。候補は1行にまとめ、チャンネル名のすぐ右に「ぐりすぺ」「れぞらぶ」のチップを表示する。選択済みの投稿先も同じ表記に揃える。長いチャンネル名は省略し、全文と接続先のURLをツールチップで確認できるようにする。同名でもサイト名で区別して選べるようにする。片方の取得が失敗しても、成功した側は選択でき、失敗した側だけ再試行できる。「もっと見る」は1つにまとめ、押すと続きがある両サイトからまとめて取得する。片側が失敗しても正常な側の続きを読めるようにし、失敗した側の再取得も同じ操作で行う。続きを読み切って失敗した側だけが残ったら、同じ位置に「再試行」を表示する。取得中はボタンを無効にして二重の読み込みを防ぐ。サイトごとの続きの位置は内部で管理する。以下の初期ワイヤーフレームと異なる点は、この更新を優先する。

デスクトップはダイアログ（既存の `*Dialog` パターンに準拠、中央配置・背景オーバーレイ）、モバイルは画面下からの全高に近いシート（既存の `*SheetDialog` / drawer パターンに準拠）とする。実装クラス名は提案であり、実際には既存の `os.popup` / `MkModalWindow` 等の確立されたダイアログ機構に乗せる想定。

```
┌────────────────────────────────────────┐
│ 投稿先を選ぶ                        [✕] │
│ ┌──────────────────────────────────┐ │
│ │ [✓] 通常の投稿（通常タイムライン）     │ │ ← 最上部・固定・常設
│ └──────────────────────────────────┘ │
│ ┌────────────────────────────────┐ │
│ │ 🔍 チャンネルを検索…              │ │
│ └────────────────────────────────┘ │
│ お気に入り                            │
│  [✓] #A  れぞらぶ   短い説明…         │
│  [ ] #B  れぞらぶ   短い説明…         │
│ フォロー中                            │
│  [ ] #D  れぞらぶ   短い説明…         │
│ 最近使った                            │
│  [ ] #E  れぞらぶ   短い説明…         │
│ 検索結果（"abc"）                      │
│  [ ] #C  ぐりすぺ   連携先への掲載は準備中（選択不可）│
│  [ ] #F  れぞらぶ   アーカイブ済み（選択不可）       │
│                                      │
│ 通常の投稿＋2件のチャンネルを選択中  [投稿欄へ戻る] │
└────────────────────────────────────────┘
```

- **「通常の投稿」はシート最上部に固定のチェック項目として常設する**（**提案**、今回の方向修正の中心）。チャンネル候補のリスト（お気に入り/フォロー中/最近使った/検索結果）とは視覚的に区切り線で分離し、スクロールしても常に見える位置に置くか、少なくともリストの先頭に固定表示する。
- チャンネル候補のセクション順（**提案**）: お気に入り → フォロー中 → 最近使った → 検索結果。検索語が空のときは検索結果セクションを出さない。既存API `channels/my-favorites`、`channels/followed`、検索は `channels/search` を使う（`plans/multi-note.md` 記載）。遠隔候補は段階1では `gridspace/channels` を**表示のみ**に使い、選択不可で描画する。
- 各行の構成要素（**提案**のレイアウト、データsourceは既存API由来）: チェックボックス／選択状態 → チャンネル名 → 発信元バッジ（「れぞらぶ」「ぐりすぺ」等、色だけに依存しない文字ラベル）→ 説明文の先頭（1行で省略） → センシティブ/選択不可の理由ラベル。
- 同名チャンネルが複数発信元に存在する場合、発信元バッジで区別する（`plans/multi-note.md` の `MkCombinedChannelList.vue` 言及に対応）。お気に入り・フォロー中・検索結果に同じチャンネルが重複して出る場合は1行に統合し、どのセクション由来かは行内の小さなタグで示す（**提案**）。
- **チャンネル数の固定上限は設けない**。候補が多い場合は検索欄での絞り込みと、選択済みチャンネルを一覧上部（または「選択中」セクション）にまとめて表示することで対処する（候補リストが長くなっても選択済みを探し直さずに解除できるようにする、**提案**）。フッターには選択内訳（「通常の投稿＋N件のチャンネルを選択中」または「N件のチャンネルを選択中」）のみを表示し、「最大◯件」の表記はしない。
- 「通常の投稿」とチャンネルの両方が0件になる操作は許可しない。「通常の投稿」をOFFにしようとした時点でチャンネルも0件なら、トグル自体を無効化し理由（「投稿先が必要です」）を示す。逆にチャンネルの最後の1件を外そうとした時点で「通常の投稿」もOFFなら、同様にその解除を無効化する。
- 各候補行はチェックボックス状態を持つ**単一のフォーカス可能な要素**として実装する（行全体が1つの `role="checkbox"` / `aria-checked`、またはネイティブ `<input type="checkbox">` をラベルで囲う形）。ボタンの入れ子やクリック領域の二重化（例: `<button>` の中に別の `<input type="checkbox">` を置く構成）は、無効なDOM構造・二重操作を招くため避ける。「通常の投稿」の固定チェック項目も同じ実装パターンに揃える。

## 3. 操作遷移

```
[通常の投稿欄を開く]
        │
        ├─ 新規に開いた場合 → 既定で「通常の投稿」=ON、チャンネル=0件
        ├─ チャンネル画面から開いた場合 → 既存互換で「通常の投稿」=OFF、そのチャンネルのみ選択済みで開始
        │
        ▼
  投稿先行をタップ/クリック（[+ チャンネルを追加] または [チャンネルを変更]、あるいは「通常の投稿」チップを直接トグル）
        │
        ▼
  投稿先シートを開く（フォーカスは検索入力へ。「通常の投稿」の固定行は常に見える）
        │
        ├─ 「通常の投稿」をトグル → 他の選択に関わらず即時反映（最後の1つを外す操作のみブロック）
        ├─ 検索語を入力 → チャンネル候補を絞り込み（既存チャンネル検索APIの非同期応答を待つ間はシート内にスピナー）
        ├─ チャンネル行をトグル → 即時に選択状態を更新、フッターの件数を更新（上限はないため「上限到達」分岐はない）
        │     └─ 選択不可の行をタップ → フォーカスは外れずツールチップ/理由テキストを表示するのみ（状態は変化しない）
        ├─ Escキー → シートを閉じて投稿先ボタン/チップへフォーカスを戻す（選択内容は保持）
        ▼
  [投稿欄へ戻る] をタップ、またはEsc
        │
        ▼
  投稿欄に戻り、「通常の投稿」チップ＋チャンネルチップ列と状態文が選択内容を反映
        │
        ├─ チップの× → その場で1件解除（シートを開かずに済む。最後の1件かつ唯一の投稿先なら無効化）
        │
        ▼
  チャンネルを1件以上選んでいて公開範囲がpublic以外 → 投稿先行の下に案内（「公開範囲をパブリックに切り替えてください」）、ワンタップ切替ボタンを提示
        │     └─ 切り替えるまで投稿ボタンは無効（送信不可）
        ▼
  本文を書く → [投稿] をタップ
        │
        ▼
  送信中（投稿ボタン・投稿先編集をロック）
        │
        ├─ 全件成功 → 成功表示（投稿詳細への**単一の**リンク + 掲載先チップ、連合有無の注記）
        ├─ 一部失敗（段階2以降で発生、段階1はローカルのみなので基本発生しない）→ 部分失敗表示
        └─ 送信失敗（通信不能等）→ 選択と本文を保持し再試行導線
```

## 6. キーボード操作・スクリーンリーダー対応

### 6.1 投稿欄本体

- タブ順: アカウントボタン → 公開範囲ボタン（既存のまま・常に表示）→ その他の設定 → 投稿ボタン（ヘッダー内、既存DOM順）→ 投稿先行（「通常の投稿」トグル → チャンネルチップ列 → 追加/変更ボタン、新規・ヘッダー直下の独立行）→ CW → 本文 → フッターのアクションバー。投稿先行はヘッダーのスロットには属さない独立したブロックなので、DOM順としてもヘッダーの**後**・本文の**前**に置く（視覚的な配置と同じ順序にし、タブ順が見た目と食い違わないようにする）。
- 「通常の投稿」トグルは個別のタブストップを持ち、Enter/Spaceで切替。切替直後に投稿先が0件になる操作は実行されず、`aria-live` で理由を通知する。
- 投稿先チップの×ボタンは個別にタブストップを持ち、Enter/Spaceで解除。解除後、フォーカスは次のチップ（削除時に詰まる場合は「追加」ボタン）へ移す。最後の1件かつ唯一の投稿先の場合は×を無効化し理由をaria-labelに含める。
- チャンネル追加/変更ボタンに `aria-haspopup="dialog"`、選択数を `aria-describedby` 等で関連付ける。

### 6.2 投稿先シート

- シートはモーダルダイアログとして実装し、フォーカスをシート内に閉じ込める（Tabでシート外のDOMへ出ない。既存の `MkModalWindow` 等のダイアログ機構が持つフォーカストラップに乗せる）。開いた瞬間に検索入力へフォーカスする。「通常の投稿」の固定行はシート内の最初のフォーカス可能要素の1つとしてタブ順に含める。
- Escキーで閉じる。閉じたら**シートを開いた元の要素（投稿先ボタンまたは「変更」ボタン）へフォーカスを戻す**。選択内容は保持し、Escは確定操作ではないので選択の取り消しは行わない。
- 各候補行（「通常の投稿」の固定行も含む）は**単一のフォーカス可能な要素**として実装する（行全体が `role="checkbox"` + `aria-checked` を持つ、またはネイティブ `<input type="checkbox">` を `<label>` で囲む構成）。`<button>` の内側に別の `<input type="checkbox">` を入れるような、クリック領域が二重になる入れ子は避ける（キーボード操作・読み上げ順序が不定になるため）。チャンネル行のラベル文字列には **チャンネル名＋発信元＋選択不可理由（あれば）** を必ず含める（色だけに頼らない、という計画書の要求に対応）。例: 「#C、ぐりすぺ、連携先への掲載は準備中、選択不可」。選択不可理由は見た目（行内のテキスト）とラベル（読み上げ）の両方に同じ文言で出す。
- タブ順: 「通常の投稿」固定行 → 検索入力 → セクション見出し（フォーカス不要、見出しのみ）→ 各候補行 → フッターの戻るボタン。矢印キーでの行移動は必須要件ではないが、候補数が多い場合は実装時に検討（本書では必須としない＝未決定事項に記載）。
- 選択数の変化（「2件選択」→「3件選択」）は `aria-live="polite"` な領域で通知する。送信結果（成功/一部失敗/失敗）も同様に通知する。
- 選択不可行を操作しても選択状態は変わらないことを保証し、理由テキストは視覚的にもスクリーンリーダー的にも同じ内容にする（tooltipのみに理由を隠さない）。

### 7.1 実装への影響（技術的背景の要約）

現行実装は `note.channelId` を単一値として持ち、チャンネル投稿時は `localOnly=true` を強制する。チャンネル一覧取得は `note.channelId = :id`、ローカルタイムラインは `channelId IS NULL`、fanout配信はチャンネルIDの有無で二者択一に分岐している。本デザインの実装ではチャンネル掲載表と通常投稿先フラグを分離し、通常投稿先は掲載表の1行として保存しない。チャンネル選択時は原本の公開範囲publicを要求し、同じ原本を重複配信・集計しない。段階2の相手原本はURI参照で扱い、ローカルIDを仮造しない。契約の詳細は `plans/multi-note-placement-protocol.md` に従う。

段階2では通常原本のミラー取得中に返信・リアクションを無効にし、取得後に同じローカル表現で操作する。専用会話は原本側に集め、本人guest返信の削除メニューを表示する。原本と会話の直接取得は既存の公開条件を使い、掲載消失後に本人限定へ切り替えない。原本の管理操作は投稿者にだけ表示する。旧Web/iOS/外部APIでは一覧が一部表示になること、掲載確認不能と解除済みの違いを案内する。

## 8. 段階2以降との差分（本デザインでの扱い）

- **段階2（連携先チャンネル）**: 投稿先シートの遠隔候補が選択可能になる。発信元バッジの意味が「表示のみの区別」から「実際の送信先の区別」に変わる。チップにも発信元を明示するレイアウト余白は段階1から確保済み（セクション2.2）なので構造変更は不要。一部失敗・再試行UI（本書「状態一覧」の該当行）は段階1でも設計上定義済みだが、実際に発生するのは段階2以降。
- **旧段階3の撤回**: 予約投稿と投稿後の掲載先追加・再追加は不要とする。予定日時のUIや掲載先を後付けするUIは設計対象に含めない。当初の掲載失敗の再試行、掲載解除、原本削除は既存の要件として維持する。
