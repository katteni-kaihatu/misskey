# Multi Note 双方向チャンネル掲載契約案 設計レビュー

## 結論

原本1件、URIで参照する掲載、両サーバーの許可が揃って初めて表示、ActivityPubの形式は変えない。この骨格は妥当です。一方で、既存ブリッジの前提とぶつかる設計判断が7件決まっていません（P0）。既存の「チャンネル側に原本を置く」方式との併存、リンク開始方向が持つ意味、掲載一覧と本文の所在が違う場合の水和、掲載行がない状態での削除、返信を replyId と URI のどちらで表すか、リアクションの所有、note行を前提にする従来APIです。

## 調査の基点

- ぐりすぺ `codex/gridspace-bridge` が `9a15160548`、れぞらぶ `codex/gridspace-bridge` が `57ee8ed337` であることを確認しました。
- 主要ファイルのblobハッシュは両リポジトリで一致しています: `peer-protocol.ts`、`GridspaceChannelAuthService.ts`、`GridspaceChannelService.ts`、`GridspaceReplyService.ts`、`GridspaceReactionService.ts`、`TimelineMergeService.ts`。
- `GridspaceNoteService.ts` だけblobが異なります。この差分の中身は確認していません。
- 以下の行番号はぐりすぺブリッジのものです。計画ファイルの行は `plans/multi-note-placement-protocol.md` を「契約案」、`plans/multi-note-peer.md` を「peer」と表記します。
- 読み取り操作だけで調査しました。

## 指摘

### P0-1【意思決定不足】既存channel-post（チャンネル側に原本、作者はゲスト）と新契約の併存

- **根拠:**
  - `GridspaceReplyService.ts:89` の `fetchAndCreate` は、チャンネル側で**ゲストの `MiRemoteUser` を作者とするnote行**を作ります。
  - `:120` のとおり、投稿者は常に自分のIDのゲストです。
  - 契約案L55は既存 `channel-post` を維持し、L66は「actor URIがそのサーバーの投稿者」、つまり原本の所在＝作者のサーバーを前提にしています。
- **失敗例:** ぐりすぺ利用者が、れぞらぶ#Aだけを選んで投稿します。
  - 旧経路なら原本はれぞらぶ側にでき、canonicalUriはれぞらぶ、作者はぐりすぺのゲストです。
  - 新経路なら原本はぐりすぺ側です。
  - 同じUI操作なのに、削除権（`peerDelete` の `note.userId` 一致）、返信の保存先、本人のプロフィール表示が変わります。
  - さらに旧投稿では「原本の所在＝作者のサーバー」が成り立たないため、この前提で組む返信・リアクションの振り分けが壊れます。
- **推奨:**
  - 新UIからの相手チャンネル投稿は新契約に一本化し、`channel-post` は旧クライアント（iOS `NativePeerChannel.swift` を含む）専用として凍結します。
  - 参照形式に `authorOrigin` を加えるか、旧投稿を「`noteOrigin = channelOrigin`、作者は別origin」と明示します。

### P0-2【計画不足】双方向化を妨げているのは `channelRole` だけではなく `link.initiator` もある

- **根拠:**
  - クライアント側: `GridspaceChannelAuthService.ts:34` で、リンクを開始していない側（非initiator）の利用者は `AUTHORIZATION_REVOKED` になります。
  - ソース側: 逆にinitiatorのリンクを拒否します（`GridspaceChannelService.ts:41,79,96`、`GridspacePrivateService.ts:268,357,580,767`、`GridspaceReplyService.ts:54`）。
  - `channelRole` はチャンネル以外にも効いています: `collectionClient`（`PrivateService:85,561,662,755`）とホームのチャンネル取り込み（`:697`）。
- **失敗例:**
  - リンクをぐりすぺ側から開始した利用者は、れぞらぶ側で相手チャンネルを開けません。つまり利用者ごとにリンクを開始した方向で、使える方向が固定されます。
  - 両サーバーを `source` に設定すると `isClient=false` となり、ホームのチャンネル経路・collection・selfRenoteの挙動も同時に変わります。
- **補足:** peer L17の「能力を別々に表す」は方針として正しいですが、リンクの方向との結合と、`channelRole` が流用されている箇所の棚卸しが計画に入っていません。
- **推奨:**
  - サーバー能力を `channels.host` / `channels.guest` に分けます。
  - チャンネル上の本人識別をリンク方向から切り離します（P1-14と合わせて決定）。
  - `initiator` の判定箇所を全件、表にします。

### P0-3【計画不足】「掲載一覧はpeer・本文はlocal」と「一覧はlocal・本文はpeer」の水和経路がない

- **根拠:**
  - `GridspaceTimelineService.ts:117-150` では、peer参照は常に `delegated.timeline({ids: peerのnoteId})` で取得します。
  - channel種別ではローカルsourceが空です（`:83-90`）。
  - 同じURIはlocalを優先して所有者にします（`:154-155,320-324`）。
  - `TimelineMergeService.ts:53` は「Source ownership is disjoint」を前提に、`seen` を直近100件に切り詰めています。
  - ローカル参照は `TimelineReferenceService.getMany` が「Existing notes only」です。
- **失敗例:**
  - れぞらぶの閲覧者が、ぐりすぺ#B（れぞらぶ原本・チャンネル専用・作者は未フォロー）を開くとします。
  - ぐりすぺはnoteIdのない参照を返し、れぞらぶはpeer参照としてぐりすぺへ本文を要求します。ぐりすぺは本文を持たないため、原本側（れぞらぶ）へ取りに行きます。
  - 結果は往復のループか、deadline切れで空表示です。
  - 作者をフォロー中の場合はlocalが所有者になり、#B経路の情報が消えます。その後フォロー解除するとownerが変わり、`resetRequired` が連続します。
- **推奨:**
  - 参照に `bodyOrigin` を持たせ、第3の水和モード「peerが掲載を証明し、localが水和する」を定義します。
  - チャンネル側は本文を取りに行かず、掲載証明 `{viewerActorUri, placementId, generation, canonicalUri, expiresAt ≤ 60s}` を返します。水和する側はその期限でvalidForMsを下げます。
  - 所有者を1つの値で持つのをやめて「到達経路の集合」にするか、所有者を決める規則（例: 本文の所在を優先）を契約に書きます。

### P0-4【計画不足】掲載行がない状態の原本削除と、遅れて届くplace

- **根拠:**
  - 契約案L70・L120は、掲載記録の状態で遅れたplaceを拒否する前提です。
  - 既存にはURI単位の墓標とadvisory lockがあります: `MiGridspaceNoteTombstone` と `gridspace-note:<uri>`（`NoteCreateService.ts:758-759`、`NoteDeleteService.ts:75-77`）。
- **失敗例:**
  - workerがplaceを送信している間に投稿者が削除し、delete-originが別のtickで先に届きます。掲載行がないので何も起きません。
  - その後、遅れたplaceが届いてactiveな掲載が作られます。
  - 原本側の索引からは配送先が消えているため、削除は二度と届きません。チャンネル側には本文の出ない「unavailable」行が残り、投稿数・lastNotedAt・通知は増えます。
- **推奨:**
  - チャンネル側にURI単位の墓標を置きます（既存Tombstoneを再利用するか、URI単位の最大世代を記録）。
  - place・delete-origin・removeを同じadvisory lockで直列化します。
  - 「世代」はL45〜47で定義が曖昧なので、原本側がURI単位で単調に採番し、削除が最大世代を持つと明記します。

### P0-5【意思決定不足】返信を replyId と URI参照のどちらで表すかと、AP互換

- **根拠:**
  - `ApRendererService.ts:365-387` の `inReplyTo` は、replyIdの行からしか作られません。
  - `Note.replyId` はFKなしです（`Note.ts`、`createForeignKeyConstraints:false`）。
  - 契約案L108〜111。
- **失敗例:**
  - ぐりすぺ利用者が「通常＋れぞらぶ#A」の原本に返信した時点で、ミラーが未着だとします。親URI参照だけで保存されます。
  - 連合ONなら `inReplyTo` のない `Create<Note>` が第三者へ届き、独立した投稿に見えます。形式は変えていませんが、意味が壊れます。
  - 後からミラーが届くと、replyIdで付いた返信とURI参照の返信が混在し、`repliesCount`・`notes/children`・`threadId`（スレッドミュート）が分裂します。
- **推奨:**
  - 「通常投稿先がある原本への返信は、必ずミラーへのreplyIdにする（なければ既存のimport経路で先に取り込む）」と決めます。
  - URI参照は、チャンネル専用原本への会話内専用（localOnly）返信に限定します。
  - その場合の `threadId` と件数を誰が持つかも決めます。

### P0-6【計画不足】リアクションの所有モデルが既存と衝突する

- **根拠:**
  - `GridspaceReactionService.ts:29-37` は「A reactor's home server owns its complete set」です。共有ノートの集計は、相手ホストのユーザー行を除外します。
  - 契約案L112は「原本サーバーで一意性を確認」としています。
- **失敗例:**
  - 通常＋チャンネル原本（`gridspaceShared=true`）に、ぐりすぺ利用者が#Bの掲載文脈からリアクションします。原本側にぐりすぺホストのゲストとして保存されます。
  - 集計では相手ホストの行が除外されるため、**リアクションが消えます**。
  - 同じ人がミラー上でも押すと二重になります。
- **推奨:**
  - 原本の共有有無で所有者を固定します。共有原本は既存どおり押した人のサーバーが所有し、掲載文脈からの操作もミラー経由にします。チャンネル専用原本は原本側に保存します（`allRows` 経路）。
  - 投票は、ゲストとAP actorが同じ `MiRemoteUser` になるので一意制約で防げますが、方針として明記します。

### P0-7【意思決定不足】note行のない掲載を従来API・集計がどう扱うか

- **根拠:**
  - `channels/timeline`、チャンネルのストリーム、Redis fanout、`notesCount`/`lastNotedAt`、Meilisearchはすべて `MiNote` を前提にしています。
  - 統合タイムラインは `timelineEnabled` で段階的に有効化する機能です（`peer-protocol.ts:25-26`）。
  - 契約案L49は「JOINしない」としか書いていません。
- **失敗例:** ぐりすぺの従来チャンネル画面・他クライアント・iOSで#Bを開くと、れぞらぶ原本の掲載が一切出ません。投稿数とランキングも増えず、ストリームにも流れません。
- **推奨:** 相手原本の掲載を返すAPI面を、次のどれかに決めます。
  - 統合タイムラインを必須にする
  - 従来APIはローカル原本のみと明示する
  - Packed Noteに準じる軽量表現を追加する

  あわせて、集計に含めるかどうかも決めます。

### P1-8【計画不足】配送を操作ログ型にするか状態同期型にするか、と配送の責務

- **根拠:**
  - 既存 `MiGridspaceNoteDelivery` は、noteIdを主キーに `version` で合流させる状態同期型です（`GridspaceNoteService.ts:60-80` は `sync` を送り、相手が現状を取りに来る）。
  - 契約案L46は操作・request ID・内容ハッシュを持つ操作ログ型です。
  - キューは原本側にしかありませんが、L63のチャンネル管理者による `remove` はチャンネル側から原本側へ通知します。
- **失敗例:**
  - 再試行が交差すると、古いplaceが新しいremoveの後に届きます。
  - チャンネル管理者の解除通知が片側停止で失われると、原本側の索引は永久にactiveのままです。投稿者UIは「掲載中」と表示し続けます。
- **推奨:**
  - 「(canonicalUri, peerOrigin) 単位の希望状態＋version」の行にし、workerは現在の希望状態をsyncとして送ります。
  - チャンネル側にも同じ形の通知キューを置くか、原本側から定期的にstatusで照合します。
  - 既存の共有ミラー配送と、掲載のdelete-originの到着順序を定義します。

### P1-9【意思決定不足】prepareと配送の時間差、および一度も掲載されなかった原本

- **根拠:** 契約案L59・L68・L77〜83。peer L94「状態を読めないときは古い候補を有効と推定しない」。
- **失敗例:**
  - 相手が停止中に「チャンネルだけ（ぐりすぺ#B）」で投稿します。prepareの不達を拒否として扱うと、片側停止中は投稿できません。
  - prepare成功後に相手が数時間停止すると、placeの時点で短期の許可情報が期限切れになり、failedになります。
  - 権限も失っていれば恒久的な失敗となり、どの経路にも出ない原本が残ります。これはL83/L146で未決とされている「最後の掲載を外した原本」とは別の状態です。
- **推奨:**
  - prepareのタイムアウトを確定的なエラーと区別し、扱いを決めます。案: チャンネルだけならfail-fast、通常併用なら作成してpending。
  - 許可情報の期限切れは、配送の中で内部的に再prepareします。
  - 恒久failedのチャンネル専用原本を自動削除するか、本人のみ表示にするかを決めます。

### P1-10【計画不足】チャンネル一覧のページングキーと、相手が申告する時刻

- **根拠:**
  - `timeline-protocol.ts:72` の同順位の比較は `sourceId ?? noteId ?? canonicalUri` です。
  - チャンネルの走査はnote基準です（`PrivateService:414`）。
  - `timelineMicroseconds` はミリ秒×1000なので、同じ値が起こり得ます。
- **失敗例:**
  - 同じsortAtの旧note行と掲載行が、一方はnoteId、もう一方はURIで比較され、全順序が崩れます。カーソル境界で重複や欠落が出ます。
  - 原本作成時刻は相手が申告する値なので、過去の日時を入れるとカーソルより後ろに入り（late → reset）、未来の日時なら一覧の先頭に固定されます。
- **推奨:**
  - チャンネル一覧はUNIONにし、キーを (sortAt, canonicalUri COLLATE C) に統一します。
  - sortAtはplace受付時刻との差を許容範囲で検証します。
  - 部分索引 `(channelId, sortAt DESC, canonicalUri DESC) WHERE active` を置きます。

### P1-11【計画不足】変更通知がnoteIdを前提にしている

- **根拠:**
  - `PrivateService:276-301` は `event.noteId` で差分を判定します。
  - outboxのトリガーは `note` と audience表だけで、チャンネルの方針変更は `isSensitive` だけが対象です（migration `1794875013623` L28-56）。
- **失敗例:**
  - 掲載解除のイベントをnoteIdなしで記録すると、`changed` の判定に乗らず、TTL（60秒）まで表示が残ります。
  - 逆に `affectedUserId` もnullにすると方針変更として扱われ、全セッションがresetします。
- **推奨:**
  - 掲載表と原本側の索引にトリガーを付け、canonicalUriを必須にした専用kind（16文字以内）で記録します。
  - peer側の差分判定をURI基準に改めます。

### P1-12【意思決定不足】チャンネル側サーバーのポリシーが評価されない

- **根拠:**
  - 既存のチャンネル投稿は、チャンネル側の `NoteCreateService` とレート制限（`ReplyService:86`）を通ります。
  - 新しいplaceは本文を運びません（契約案L59・L62）。
  - L68の「迂回しない」が、どちらのサーバーの規則を指すのか曖昧です。
- **失敗例:** ぐりすぺの禁止語・センシティブ語・ロール方針・ゲストへのレート制限が、ぐりすぺ#Bへの掲載で一度も評価されません。
- **推奨:** 次のどちらかに決めます。
  - placeで評価用に本文を送る（保存はしない）。
  - 原本側のポリシーだけで良いと両サイトの運営が合意し、明記する。

  チャンネル側のレート制限はplaceに適用します。

### P1-13【計画不足】返信索引の依存方向・可用性・通知

- **根拠:** 契約案L110。Misskeyの通知はローカルnote行のIDを前提にしています。
- **失敗例:**
  - 原本の会話を開くと、相手側の返信本文は相手サーバーからしか取れず、片側停止で会話が欠けます。
  - 索引の登録が失われると、作者に通知が作られません。
- **推奨:**
  - 索引の登録も、P1-8と同じ状態同期型の永続配送に含めます。
  - 通知を既存の `GridspaceNotificationService` のpeer経路で作るかを決めます。
  - 会話の部分欠落（unavailable）を契約に入れます。

### P1-14【意思決定不足】チャンネルを見る・フォローする本人の識別

- **根拠:**
  - 閲覧は、リンクを開始した側ならリンク済みアカウント、そうでなければゲストです（`ChannelAuthService:30-41`）。
  - 投稿は常に自分のIDのゲストです（`ReplyService:120`）。
- **失敗例:** 同じ人のフォロー・ミュート・BAN・削除権が2つの識別に分かれます。たとえばリンク済みアカウントでミュートしたのに、ゲスト側の経路では表示されます。
- **推奨:** 識別を1つに固定し（推奨: 常にゲスト）、既存のリンク経由フォローの移行方針を決めます。

### P2-15【計画不足】信頼モデルの明文化

- **根拠:** 署名は1組の共有HMAC鍵で、peerも1つです（`peer-protocol.ts` の `signature`）。L66の「送信originが原本originと一致」は常に真になります。
- **推奨:**
  - 「原本側が独立に保証する条件」と「チャンネル側の申告に依存する条件」を表にします。
  - place/readでは、`validateGridspaceBundle` と同じURIのprefix検証と `/activity` の正規化を必須にします。

### P2-16【計画不足】掲載先チップの部分失敗

チップには両サーバーの掲載情報が必要です。片側の取得に失敗した場合は「チップなし」として扱い、解除と同じ意味にしないことを契約に書きます。

### P2-17【意思決定不足】受付記録の保持期間

- 既存の `MiGridspaceReplyReceipt` は削除後も永続保持です（`Gridspace.ts:134`）。
- 契約案L72は保持期間を未決としています。
- 保持期間がクライアントの最大再試行期間より短いと、削除済みの原本が再作成されます。保持期間は「最大再試行期間以上」と下限を決めます。

## 判定

### 契約として固められる部分

- 原本は「投稿者として選んだアカウントのサーバー」に1件置き、actor URIは自動で変えない（L23）。
- 相手側には本文を保存しない掲載参照を置き、`(channelId, canonicalUri)` を一意にする。`originNoteId` をローカルのnote IDとして扱わない（L45・L49）。
- 両サーバーの許可が揃って初めて表示する（L51・L100）。一時的なunavailableと、解除・削除・失効を区別する（L102）。
- capabilityが一致するまで相手の掲載先を選べなくする。表示更新用のoutboxと永続配送を分け、イベントは許可の証明にしない（L122）。
- 原本作成の冪等キーと内容ハッシュを持つ。削除後の再送で原本を再作成しない（L72）。
- ActivityPubの形式は変えず、チャンネル専用は配送しない。初期の対象は公開・非センシティブ・`public` 必須とする。

### 実装前に決定が必要な部分

- **P0:**
  - 旧channel-postとの関係（P0-1）
  - 能力の分離とリンク方向からの切り離し（P0-2）
  - 水和モードと所有者の規則（P0-3）
  - URI単位の墓標と世代の定義（P0-4）
  - 返信の表現（P0-5）
  - リアクションの所有者（P0-6）
  - 従来APIと集計での扱い（P0-7）
- **P1:**
  - 状態同期型の配送と双方向のキュー（P1-8）
