# スペース(同期コミュニケーション)デザインと計画

2026-11-26 時点の検討結果。まだ案を練っている段階で、実装は始めていない。

- デザインのキャンバス: https://claude.ai/artifact/NqqUbUF9PiSPyiGuQB4Ysp (非公開。共有するには作成者がページの Share から共有する)
- 参考にした試作: https://github.com/katteni-kaihatu/tonarium-prototype

## 1. 何を作るか

ぐりすぺ(misskey.grid-space.io)に、Twitter のスペースのように都度ひらく、同期的に集まれる場所を足す。中の UI と体験は Discord の通話に近づける。

- 通話は任意。声を出さずに居られる。
- 中で画面共有ができ、みんなで触れる部品(タイル)を置ける。
- 表示のひとつとして 3D があり、VRM アバターで入れる。
- タイルも 3D のアイテムも、ユーザーが自分で作って配れる(UGC)。

## 2. 決めたこと

| 項目 | 決定 | 補足 |
| --- | --- | --- |
| 開き方 | 都度ひらく | 仮決め。常設の部屋にはしない |
| 中の画面 | Discord 寄りの通話画面を基本形にする | ボード型(A案)・ステージ型(B案)は不採用 |
| 声 | 全員に同じ大きさで届く | 距離による減衰は入れない。3D で歩く場所は見た目だけ |
| 3D の位置づけ | 同じ通話の「表示のひとつ」 | 2D と 3D は切り替えるだけで、通話・人・タイル・チャットは共通 |
| 入り方 | 聞くだけ / 話す / 文字だけ から選ぶ | 既定は聞くだけ。入った直後は必ず音を出さない |
| アバター | VRM は任意 | 既定はアイコンを顔にした簡易の姿 |
| 終わったあと | まとめがノートになる | タイルと配置は残り、「続きをひらく」で引き継ぐ。チャットと声は残さない |
| UGC | タイル(2D)とアイテム(3D)の2種類 | 作り方は段階を分ける(5章) |
| 連合 | しない | ぐりすぺ独自の機能で、ActivityPub には流さない。入れるのはこのサーバーのユーザーだけ |
| 開始・まとめノートの範囲 | ホストが毎回選ぶ | ひらく画面に選択肢を置く |
| 入れる人 | サーバーの全員 / フォロワーだけ | スペースはリンクを持つ。リンクは入口で、入れるかは入るたびにサーバーが判定する(リンクを知っているだけでは入れない)。公開範囲はひらいたあとでも変えられ、すでに中にいる人は追い出さない |
| お知らせノートの形 | 本文にスペースのリンクを入れた普通のノート | このサーバーではリンクをカードに描き替える。ほかのサーバーにはリンクつきの普通のノートとして届く |
| だれもいなくなったとき | 30分で自動で閉じる | ホストの閉じ忘れへの備え |
| ひらける人 | ログインユーザー全員 | 制限は設けない |
| 話せる人 | だれでも話せる | ホストは個別にミュートや追い出しができる |
| タイル・アイテムを置ける人 | 全員。ホストが絞れる | ホストは「ホストだけ」に切り替えられ、他人が置いたものを片づけられる |
| カメラ | あと回し | 最初は声と画面共有だけ。絵のボタンは外す |
| スマホの 3D | 最初は PC だけ | スマホは 2D と視点ライブで参加する |
| 3D の部屋 | グリッドスペース | グリッドの床だけがある空の空間から始める |
| 終わり方 | ホストが閉じるまで続く | ホストの回線が切れても閉じない。戻ってくれば続けられる |
| 通話の基盤 | LiveKit を自前で動かす | 声と画面共有をまとめて扱う。いまの Misskey と同じホストに、別コンテナで足す |
| スペースの状態の持ち方 | サーバーがスペース全体の情報を持つ | いる人、タイル、アイテム、配置、共有する値の正はサーバー。サーバーは覚えて配るだけで、計算はしない(5.5、5.6) |
| 処理の場所 | 各自のブラウザ(ローカル処理) | スクリプトも物理も手元で動かす。全員の手元で同時に起きる出来事は、担当の1人だけが実行する(5.5)。サーバーでユーザーのコードは動かさない |
| UGC の言語 | 全部 JavaScript | タイルは HTML と JavaScript で自由に作る。アイテムとゲームも JavaScript。AiScript は使わない。既存の Play は「Play」のタイルで丸ごと置ける(5.1) |
| スクリプトの権限 | 読むのはよい。投稿は本人がボタンを押す | スクリプトは情報の取得(GET)ができる。外部の URL は許可制で、許可したホストか本人のブラウザから送る。投稿はスクリプトが勝手に行わず、投稿ボタンを出して本人が押す(5.7) |
| 進め方の優先 | プロトタイプを回すことを優先 | 30人ほどのコミュニティなので、スクリプトの安全対策は最初は緩くてよい。最終的には必須 |
| 上限 | 設けない | 小さいコミュニティなので、人数・ファイルサイズ・個数にスペース独自の上限は作らない。ファイルはドライブに置くので、ドライブ側の既存の上限だけが効く |

Tonarium から取り入れたのは「表示を変えても同じ集まりにいる」「同じ物にそれぞれの画面から働きかける」「続きを持ち越す」の3点。距離で声が変わる仕組みと、2D の人にも位置を持たせる仕組みは取り入れない。

## 3. 画面

キャンバスの並びに対応する。

### 3.1 見つけて、入る、終わる

- **タイムラインの入口**: 上部に「いま開いているスペース」の棚。開始ノートにはスペースのカードが付く。参加したままタイムラインに戻ると、下にミニバー(誰が話しているか、マイク、退出)が出る。
- **スペースをひらく**: ホストが、名前、声の有無、入れる人、お知らせノートの範囲、前回の続きから始めるか、タイルを置ける人を決める。3D の部屋はグリッドスペース固定なので選ばない。
- **入り方を選ぶ**: 入る前に、誰がいて何が置いてあるかを見せる。聞くだけ / 話す / 文字だけ を選んで入る。
- **スペースのまとめ**: 終了時にホストのノートとして投稿する。来た人、残ったタイル、「続きをひらく」を載せる。

### 3.2 スペースの中(通話画面)

- **中央**: 画面共有・3D の視点ライブ・タイルのどれかを大きく出す。何を出すかは人ごとに選ぶ。
- **下**: 通話にいる人と、ほかの共有が並ぶ。話している人には枠が付く。
- **右**: 「タイル / チャット / いる人」のタブ。画面共有を見ながらタイルを触れる。
- **操作バー**: マイク、画面を共有、リアクション、タイルを置く、出る。キャンバスの絵にはカメラのボタンが残っているが、あと回しにしたので外す。
- **モバイル**: 上に共有画面、下にタブ。スマホは見る側だけで、画面の共有は PC から行う。

### 3.3 3D 表示と VRM

- 2D / 3D の切り替えをヘッダーに置く。切り替えても通話は切れない。
- タイルは 3D では板として立つ。共有画面も大きな画面として立てられる。
- 2D で参加している人は、3D の中では顔の札として見える。
- 3D を開かない人は、3D の人の「視点ライブ」で中の様子を見られる。
- VRM の設定では、3D での姿と、そこから作る 2D 用の顔を確認できる。ファイルに書かれた利用条件を表示する。

### 3.4 置く・つくる

- **タイルを置く**: きほん8種(ノート・画像・投票・やること・らくがき・メモ・リンク・Play)と、みんなが作ったタイルの一覧。
- **タイルをつくる**: コード、置いたときのプレビュー、操作できる人の設定。

### 3.5 まだ描いていない画面

- 通話画面の PC 版で、共有がないとき
- 3D 表示で、共有画面が部屋の中に立っている様子
- アイテムを出す / アイテムをつくる
- ゲームに参加する / スコアボード

## 4. UGC の全体像

| 種類 | 何か | 見える場所 | 例 |
| --- | --- | --- | --- |
| タイル | 2D のパネル | 2D と 3D の両方(3D では板) | 投票、タイマー、お題ガチャ |
| アイテム | 3D の中の物 | 3D だけ。2D には「3D で3人が遊んでいる」程度 | ボール、椅子、水鉄砲 |
| ゲーム | スペースに置くルール | 参加した人だけに効く | 雪合戦、鬼ごっこ |
| 部屋 | 3D 空間そのもの | 3D だけ | `.glb` で差し替え |

アイテム・ゲーム・タイルは、1つのパッケージとしてまとめて配れるようにする(例: 水鉄砲 + 雪合戦のルール + スコアボード)。

## 5. UGC の作り方(段階)

### 5.1 タイル

HTML と JavaScript で書く。見た目は自由に作れる。

タイルは、権限を絞った埋め込み枠(sandbox 付きの iframe)の中で動く。枠の中からは Misskey のアクセストークンにも保存データにも触れず、外への通信もできない(5.7)。外とのやり取りは、本体が枠に渡す `space` という窓口だけを通す。

`space` は提案中の API で、細部は未定(8章)。

- `space.shared`: 全員で共有する値。読む、書く、変化を受け取る。サーバーが保存し、途中参加の人にも届く。
- `space.mine`: 自分だけの値。
- `space.send` / `space.on`: 保存しない一時的な知らせ(描いている途中の線、カーソルの位置など)。その場にいる人にだけ届く。
- `space.me` / `space.members` / `space.isHost`: いる人の情報。
- `space.fetch`: 外部の URL の取得。許可制(5.7)。
- `space.postButton`: 本文を入れた投稿ボタンを出す。押すのは本人(5.7)。

通信の流れ。

1. タイルが `space.shared` に書く。
2. 枠から本体へ伝わる(ブラウザの枠間通信)。本体はすぐ手元の表示に反映する。
3. 本体が Misskey のストリーミング(WebSocket)でサーバーへ送る。
4. サーバーが順番を決めて保存し、スペースの全員へ配る。
5. 各自の本体が受け取り、それぞれの枠の中のタイルへ渡す。

タイルは自分で通信路を持たない。すべて本体を通るので、許可の確認や量の制限を本体の1か所でかけられる。共有する値はタイルごとに分けて持ち、ほかのタイルの値は読めない。同じパッケージのタイル・アイテム・ゲームは値を共有できる。

画像などの素材は、ドライブに置いたものだけを読み込める。

既存の Play(AiScript)は、きほんのタイルの「Play」で丸ごと置ける。Play のコードをタイルに書き換えて使うことはできない。

### 5.2 アイテム

1. **モデル + ふるまいを選ぶ(コードなし)**: `.glb` を上げて、「持てる / 座れる / 蹴れる / 押すと音が鳴る / 光る」から選ぶ。
2. **スクリプトで反応を書く**: 「押された」「拾われた」「ぶつかった」などのイベントに反応する処理を書く。重い計算(物理、補間、弾の飛行)は本体が受け持ち、スクリプトは指示を出す。JavaScript で書き、タイルと同じく隔離した枠の中で動かす。three.js には直接触れず、`space` を通して「この箱を動かす」のように本体へ頼む。
3. **本体の中身に直接触れる自由なコード**: 当面やらない。スクリプトから使えるのは本体が渡した機能だけにする。1 と 2 で足りないと分かってから検討する。

毎フレームの処理(OnLoop)は各自の手元で動くので、見た目の演出(回る、光る、ゆれる)には使ってよい。共有する値を毎フレーム書き換えるのは避け、出来事が起きたときだけ書く。

### 5.3 銃や PvP を作れるようにする部品

本体側に次の部品を用意すれば、5.2 の 2 の範囲で作れる。

- 「使う / 持つ」の入力
- レイキャストと弾(当たった相手を返す)
- プレイヤーごとの値(HP、スコア、チーム)
- リスポーンとテレポート
- HUD(タイルを画面に重ねる)

ルール(勝敗、ラウンド、チーム分け)はアイテムではなく「ゲーム」のスクリプトに書く。

### 5.4 割り切ること

- **参加制**: 「ゲームに参加」を押した人だけが撃たれる対象になる。スペースは通話の場なので、押していない人には何も起きない。
- **当たり判定は撃った人の画面が正**: 最初はこの方式にする。チートは可能だが、身内のコミュニティでは許容する。
- **物理の同期は「持っている人の画面が正」**: それ以上の厳密な同期はしない。
- **届くのはパーティーゲームまで**: 競技レベルの FPS は対象外。
- **重さと安全**: VRM・アイテム・部屋のファイルはドライブに置き、既存の通報や NSFW の仕組みに乗せる。スペース独自の上限は設けない。重いときは見る側で対処できるように、相手側で「VRM を表示しない」「他人のアイテムを表示しない」「他人のスクリプトを動かさない」を選べるようにする。

### 5.5 状態と処理をどこで持つか

状態はサーバーが持ち、処理は各自のブラウザで動かす。VRChat や Resonite と同じ、ソーシャル VR で主流の型。

- **サーバーは状態を持つ**: いる人、タイル、アイテム、配置、共有する値(票、タイマー、HP、スコア)はサーバーが持ち、書き込みの順番を決めて全員に配る。途中参加の人には今の状態を渡せて、「続きをひらく」用の保存もそのまま残せる。サーバーは計算をせず、ユーザーのコードも動かさない。
- **処理は手元で動かす**: タイル・アイテム・ゲームのスクリプトと物理は、各自のブラウザで動く。操作した人の画面は、サーバーの返事を待たずにすぐ変わる。
- **自分の操作がきっかけの出来事**: 押した、拾った、撃ったは、その人の手元で実行し、結果を共有する値に書く。
- **全員の手元で同時に起きる出来事**: タイマーが切れた、物同士がぶつかったなどは、そのままだと人数分実行される。これは「担当」の1人の手元だけで実行する。物ごとの持ち主は作らない。
- **担当の決め方**: 既定はホスト。ホストがいないときは、在室がいちばん長い人に自動で移す。3D の中の出来事(ぶつかった など)は 3D を開いている人しか計算できないので、3D を開いている人の中から同じ規則で選ぶ。3D を開いている人が1人もいなければ、3D の中の出来事は止まる。
- **だれもいないとき**: スクリプトは動かない。状態はサーバーに残り、次に人が入ったところから続く。
- **将来**: サーバーで判定したいゲームが出てきたら、そのときサーバー側の処理を足す。

### 5.6 遅延を減らす方針

体感の遅延は、配る経路よりも「何を待たずに表示するか」で決まる。

1. **自分の操作は待たない**: 歩く、持つ、撃つ、投票するは、押した瞬間に手元で確定させる。サーバーにはあとから伝え、食い違ったときだけ直す。
2. **他人の動きは補間する**: 届いた位置をなめらかにつないで表示する。0.1 秒ほど過去を見ることになるが、カクつきを防げる。
3. **サーバーは確定と保存の役**: 受け取ったらためずにすぐ配る。順番を決めて今の状態を覚えておくのが仕事で、毎フレームの計算はしない。

配る経路は2本に分ける。

| 情報 | 経路 | 理由 |
| --- | --- | --- |
| 声・画面共有 | LiveKit(UDP) | 遅延がいちばん気になる部分 |
| アバターの位置、弾 | LiveKit のデータ通信(UDP、届かなくてもよい設定) | 古い位置は再送しても意味がない。落ちても次の位置で上書きできる |
| 票、タイマー、HP、配置、チャット | Misskey のストリーミング(WebSocket) | 1つも落とせない。頻度が低いので遅延は問題にならない |

- 位置は LiveKit で配りつつ、サーバーにも毎秒1回ほど写す。サーバーが全体を持つ方針と両立し、途中参加の人にもおおよその位置を渡せる。
- LiveKit も Misskey も同じホストにあるので、どちらの経路もサーバーを1回経由する点は同じ。差が出るのは回線が不安定なときで、WebSocket は1つの遅れが後ろを止めるが、UDP は止まらない。
- 実装は、最初は全部を Misskey のストリーミングで配り、3D の段階で位置だけ LiveKit に移す。配る部分を1か所にまとめて作り、差し替えを小さくする。
- 当たり判定は撃った人の画面が正なので、撃った手応えは遅延なし。撃たれた側が少し遅れて知るのは割り切る。

### 5.7 スクリプトの安全と権限

他人が書いたスクリプトが自分のブラウザで動く。サーバーでは動かないので、守る対象は各自の画面とアカウントになる。

1. **隔離した枠で動かす(最初から入れる)**: スクリプトを Misskey の画面の中でそのまま動かすと、アクセストークンを盗める。権限を絞った埋め込み枠(sandbox 付きの iframe)の中で動かす。枠の中は別の出どころとして扱われ、トークンにも保存データにも触れない。
2. **枠からの通信を止める(最初から入れる)**: 枠にセキュリティ設定(CSP)を付けて、外への通信をすべて禁止する。スクリプトは本体に頼むしかなくなり、外部への GET の許可制を仕組みとして守れる。
3. **暴走を止める(あとでよい)**: 枠の中でワーカーを使って動かし、無限ループに入ったらそのワーカーだけ止める。
4. **見る側が止められる**: 「他人のスクリプトを動かさない」を選べる。止めた人の画面では演出が動かないが、共有する値は届く。
5. **作者を必ず表示する**: HTML で自由に描けるので、Misskey のログイン画面に似せたタイルも作れる。タイルの枠に作者名を必ず出し、本体の画面と見分けられるようにする。

ブラウザごとの細かい挙動は、実装のときに確かめる。

スクリプトに渡す機能の線引き。

- **スペースの中の値**: 読み書きできる。
- **情報の取得(GET)**: Misskey の公開情報は許可なしで取得できる。
- **外部の URL への GET は許可制**: スクリプトが勝手に外へ通信することはない。許可を出すのはホストか操作した本人で、通信は許可した人のブラウザから直接送る。許可の画面には宛先を表示する。サーバーは外へ通信しない。
  - ホストが許可する場合: アイテムを置くときに「このアイテムは次の宛先に通信します」と確認する。取得は担当(既定はホスト)の手元で1回だけ行い、結果を共有する値に書いて全員に配る。
  - 本人が許可する場合: 自分の操作がきっかけで通信が起きるときに、その人に確認する。取得はその人の手元で行う。
  - 担当がホスト以外に移ったとき: 新しい担当に許可を求める。断られたら、ホストが戻るまで外部の取得は止まる。
- **制約**: ブラウザから直接送るので、ブラウザからの取得を許していない外部サービスは使えない。邪魔になってから、Misskey が中継する方式を検討する。
- **投稿**: スクリプトは投稿できない。本文を入れた投稿ボタンを出し、本人が押したときに本人の操作として投稿する。Play の投稿フォームのボタンと同じ考え方。

### 5.8 3D の描画エンジン(案)

まだ合意していない案。

- `three`(three.js)と `@pixiv/three-vrm` を続けて使う。すでに入っていて、VRM との相性がよい。
- 当たり判定・物理・レイキャスト用に物理ライブラリを足す。候補は Rapier。物理は各自の手元で計算し、持っている人か担当の結果を正とする(5.4、5.5)。
- アイテムの書式は three.js に直結させない。「箱をここに置く」「押されたら光る」のような言葉で書き、three.js に翻訳する層を1枚はさむ。エンジンを入れ替えても過去の UGC が壊れず、AI から見える仕様も安定する。

### 5.9 AI に作らせる(案)

まだ合意していない案。3D の UGC を AI が作れることを目指す。

- **アイテムを1つのテキストファイルにする**: 形(箱・球・円柱などの組み合わせ)+ ふるまい(選択式)+ スクリプト。文章として書けるので AI が得意で、ファイルが小さく、あとから直せる。
- **説明書と検査を用意する**: 書式の説明と例、間違いを具体的に返す検査。AI はエラーを読んで自分で直せるので、ここの出来が成功率を決める。
- **MCP をクラウド経由で提供する**: 各自が手元の AI に URL を登録すると、スペースにアイテムを置ける。サーバー側の AI 利用料はかからない。通常の API を先に作り、MCP はそれを包む薄い層にする。同じホストの別コンテナで動かす。
- **MCP の道具**: 書式の説明を取る、検査する、作る / 直す、スペースに置く / 片づける、スペースの状態を見る、見た目を撮る、エラーを読む。
- **エラーを読む**: スクリプトは各自のブラウザで動くので、エラーもブラウザで起きる。作者本人か担当のブラウザがエラーをサーバーへ送り、AI はそれを読む。
- **見た目を撮る**: 3D は置いてみないと正しいか分からない。3D で参加中の誰かのブラウザに撮影を頼み、画像を AI に返す。視点ライブと同じ仕組みを使う。
- **認証**: 最初は各自が発行したアクセストークン。「アイテムを作る・置く」だけに絞った権限を新設する。OAuth でのログインは、Misskey の OAuth が MCP の求める方式と噛み合うかを確認してから。
- **メッシュ生成**: 文章から `.glb` を作る外部サービスは、`.glb` を受け入れる仕組みがあれば後から足せるので急がない。

言語は全部 JavaScript に決めた(2章)。AI がほぼ間違えずに書けるので、この案と相性がよい。タイルも同じ道具で作って置ける。

## 7. 進め方の案

各段階の終わりに、実際に人が集まって試せる状態にする。

段階1と2の実装の設計(テーブル、API、ストリーミング、LiveKit の置き方、作る順番)は [spaces-implementation.md](spaces-implementation.md) に書いた。

1. **通話だけのスペース**: ひらく・入る・出る、聞くだけ / 話す / 文字だけ、チャット、タイムラインの入口とミニバー。
2. **画面共有とまとめ**: 画面共有、終了時のまとめノート、「続きをひらく」。
3. **きほんのタイル**: 本体が用意するタイル(投票、やること、らくがき、ノート、タイマー)と、全員で共有する値の同期、担当の仕組み。
4. **自作タイル**: 隔離した枠、`space` API、作成画面、公開と一覧。
5. **3D 表示と VRM**: 2D / 3D の切り替え(PC のみ)、グリッドスペース、簡易の姿、VRM の読み込み、タイルを板として立てる、視点ライブ。
6. **アイテム(コードなし)**: `.glb` + ふるまいの選択、部屋の差し替え。
7. **アイテムのスクリプトとゲーム**: イベント API、レイキャストなどの部品、参加制のゲーム、パッケージ配布。

1〜4 は 3D なしで成り立つので、3D の作り込みを待たずに出せる。
