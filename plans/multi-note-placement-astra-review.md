## 1. 全体判定

**基盤実装には着手できます。新形式の書き込みを有効にするには、計画の修正が必要です。** 新規P0はありません。新規P1は6件です。これとは別に、Claudeの残P2のうち、②事前認可なしの配信と⑤原本側の非表示条件には、公開前にP1として扱うべき部分があります。

通常系で閲覧側の実在ミラーと行為者ホームの反応集合を使い、専用系の会話を原本側に集める方針は維持できます。旧 `channel-post` の原本・actorを保存する方針、旧 `role`・`initiator` からの認可分離、一覧と本文の所在4通り、経路の和集合、管理者解除とURI墓標の分離、旧APIの実在行だけを返す方針にも、新たな方式変更を必要とする問題は見つかりませんでした。

コードの基点はれぞらぶ `57ee8ed337`、ぐりすぺ `9a15160548` です。ぐりすぺのチェックアウトは別ブランチのため、ブリッジのGit参照を読みました。以下の「契約」は `plans/multi-note-placement-protocol.md`、コードの行番号は特記がなければれぞらぶ基点です。計画用の両 `feat/multi-note` ワークツリーには未追跡の計画文書があり、その内容を対象にしました。ファイル編集、テスト、通信、本番配備の確認は行っていません。

## 3. Claudeの残P2の評価

| 項目 | 判定 |
|---|---|
| ① 匿名証明のキャッシュ | **P2据え置き。** 同じ匿名公開条件を共有できる場合に限り、ルート・掲載・世代を単位に再利用できます。否定結果と通信障害を区別し、期限を認可期限以内に収める必要があります。 |
| ② 事前認可なしのpack | **無認可配信はP1。正当な利用者に本文が出ない場合のUIはP2。** `NoteEntityService.pack:508` は `isVisibleForMe` と別の `shouldHideNote` を使います。`NoteCreateService:904,937` は `skipHide:true` で作った本文を返信イベントにも渡し、`stream/channels/main.ts:40–69` には返信イベントの再認可がありません。`stream/Connection.ts:237–258` のノート更新も掲載経路を見ず、失効後に反応・投票等の更新情報が届き得ます。「事前認可なしならすでに隠れる」とは判断できません。受信者ごとの認可前は本文や更新情報を配信しないことを公開条件にします。 |
| ③ 専用返信の来歴の保存先 | **P2据え置き。** 本人判定と来歴を保存する要件は決まっています。`GridspaceReplyReceipt` はpeer作成が対象なので、原本サーバーのローカル利用者が作った返信も識別できる保存方法を決めます。親削除後も本人だけを識別できることは必須です。 |
| ④ 返信者本人による単体取得 | **仕様記述はP2、機能の有効化時は必須。** 契約125で既に約束しています。親・掲載消失後の本人用 `read` をホームから利用でき、親本文・他人の返信・入れ子を返さないことを確認します。削除だけに縮小するなら製品判断が必要です。 |
| ⑤ 原本側の時刻・停止条件 | **本文が開示される場合はP1。** 通常ミラー取込が作者の停止・非表示時刻で原本を拒否したのに、掲載経由の読み取り専用表示が同じ本文を返すなら、表示機能の制限では済みません。`GridspaceNoteService.ts:89–98` の拒否理由を原本側の掲載取得にも反映し、一時的な取込遅延と区別することを有効化条件にします。 |
| ⑥ `assertOwners` と掲載列の説明 | **P2据え置き。** 原本URIと利用可能経路の保持、通常ミラーの表示・操作優先は両立します。`multi-note-timeline.md:16,83`、`multi-note.md:121` の説明を契約にそろえれば足ります。 |

## 4. 実装着手と有効化の条件

**実装着手は可。** 両ブリッジの基点を合わせ、機能フラグを閉じたまま来歴、保存形式、認可、永続配送、一覧の統合を実装できます。認可証明に書込権限を載せる方法と専用添付の保管方式は、対応するAPI・DB設計の段階で先に決める必要があります。

**新形式の書き込み有効化は保留。** 最初のローカル専用投稿を許可する前から、公開フィード・埋め込み・AP Like・ファイル・ストリームの非開示と、個別削除・一括削除が必要です。遠隔チャンネルを選ばない通常＋ローカルチャンネル投稿でも、通常共有を通じて相手にミラーができます。そのため通常 `localOnly` の投票、親の一時取得不可、履歴先着時の親子関係・件数は、遠隔掲載UIの公開まで延期できません。遠隔専用会話を開く前には、書込証明、guest反応・添付、親消失後の本人閲覧・削除、通知の限定取得も必要です。

既知の `includeDefault` 移行時CHECK違反の処置、`canPublicNote` と専用投稿の扱い、`allowRenoteToExternal` と通常投稿先の組合せも、新規書き込み前の判断として妥当です。双方の対応版・全worker・移行結果を照合し、上記の条件を両方向で検証した時点で有効化を判断します。
