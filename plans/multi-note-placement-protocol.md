## 採用する公開条件と影響範囲

公開チャンネルを対象とし、センシティブ属性だけを理由に掲載対象から除外しない。「チャンネルだけ」は通常の投稿先へ配信しない指定であり、公開範囲と添付URLの扱いは既存の公開チャンネルに合わせる。

### 要件更新（2026-11-21）

- Multi Noteの予約投稿、投稿後の掲載先追加・再追加は要件から除外する。将来対応の残件として扱わない。失敗した当初の掲載要求を同じ原本で再試行する機能はM4/M8として維持し、解除済み掲載を再追加する操作とは区別する。
- センシティブな内容に必要なCWは投稿者が自分で付ける。通常・センシティブな公開チャンネルを同時に選んでも、原本の本文とCWは1つを共用する。CWの自動付与、入力必須化、掲載先ごとのCW生成、センシティブ属性の混在を理由にした専用の選択制御は要件にしない。
- 非公開・メンバー限定チャンネルのための新しい閲覧権限モデルは導入しない。既存の閲覧設定、ブロック、公開投稿権限、禁止語・センシティブ語のモデレーションはM2/M3として維持する。

旧D6にまとめていた予約投稿、掲載先の後付け・再追加、センシティブ向け追加機能の将来対応は撤回する。異なる閲覧権限モデルを導入する場合の再検討はD1に従う。

候補取得・作成検証・peer掲載・チップ取得・明示したチャンネルの一覧/ピンから、センシティブ属性だけによる一律除外を両リポジトリで撤去した。統合プロフィールも既存の掲載条件にそろえ、第三者にセンシティブチャンネル専用の投稿を一覧表示しない条件を維持する。追加の受け入れテスト20件と従来の48件が実サーバーで合格し、通常チャンネルとの同時掲載、原本のCW保持、CW未指定時の非強制、既存の閲覧条件、両方向の掲載を確認した。ブラウザでも同じCWでの掲載と逆方向のCW未指定投稿を確認した。

| 対象 | 採用する動作 |
| --- | --- |
| 通常一覧への配信 | includeDefaultで決める。専用原本・会話内返信を通常TL、通常RSS、通常共有、通常ランキングへ混入させない |
| チャンネル一覧への表示 | そのチャンネルの有効掲載がある場合だけ表示。ホームは通常経路とフォロー中の有効掲載の和集合 |
| 原本URL・標準API・会話詳細 | 既存の公開投稿の閲覧条件で取得可能。有効掲載が0件でも、その理由だけで非公開にはしない |
| 添付・サムネイル | 既存Driveの公開URL・保管・キャッシュ・再利用を維持。掲載解除でURLを失効させる保証は追加しない |
| 掲載解除・チャンネル削除 | 対象の一覧・ホームの当該経路・チップ・ピン・集計から外す。原本や別掲載先は残る |
| 原本削除・退会時の原本削除 | 原本の取得を停止し、全予定宛先に削除を配送。既存の添付保管・配信済みキャッシュの扱いは維持 |
| ブロック・停止・サインイン要求・時刻による非表示等 | 既存の閲覧制限を維持。直接URL、peer取得、pack、通知、ストリームでも迂回させない |

掲載状態と本文の公開条件を分ける。掲載解除後の公開原本を直接開けることを、解除失敗と判定しない。全掲載が失敗・解除された原本も、通常配信せず投稿者の管理画面に残すが、原本や会話を本人だけが読めるとは案内しない。原本を消す場合は原本削除を使う。

この方針により、全標準APIへpeerの閲覧証明を要求する改修、未掲載原本の本人限定化、添付配信基盤の認可付きURL化は今回の実装から外す。既存private・collectionの認可は維持する。

## 今回必須の対応

M1〜M8は対応する機能の有効化条件。後回しの改善が未完了という理由だけで基盤実装を止めない。

| ID | 必須対応 | 主な影響先と合格条件 |
| --- | --- | --- |
| M1 | 通常投稿先と掲載先の保存・配信を分離 | includeDefault、掲載表、全作成経路、DB/Redis/WebSocket、検索・推薦・RSS・通常共有。専用投稿が通常経路へ出ず、通常＋チャンネルは原本URIで1件 |
| M2 | 既存の閲覧制限と操作権限を維持 | Query/Entity、shouldHideNote、skipHideからの送信先、標準API・SSR・公開リンク・通知・ストリーム。新しい秘密投稿モデルを足さず、既存制限を迂回しない |
| M3 | 両方向の本人性・掲載/書込権限を分離 | ChannelAuth/Link/Private/Reply/Action。現在actorを維持し、閲覧用の掲載証明を返信・添付の許可に使わない。アーカイブ後は既存仕様に沿って書込を拒否 |
| M4 | 削除・退会・再送で掲載を残留/復活させない | NoteDeleteServiceとDeleteAccountProcessorServiceの双方。URI墓標、全予定宛先への永続配送、掲載・集計・ピン更新を削除トランザクションに記録 |
| M5 | 新方式で共通会話・本人操作を成立させる | 通常返信はローカル親ミラー、専用返信は原本側guest。新規取込の親未解決を独立投稿に変えず、本人削除・添付・通知・既読が両方向で成立 |
| M6 | 新方式の反応・投票を正しい対象へ送る | 通常系と専用系の分類、ExtendedReactionServiceの追加/解除、PollService/標準API/peer操作/票数・isVoted。localOnly操作をAP配送せず、同じ操作の再送で増やさない |
| M7 | 一覧・表示・旧APIを原本URIで統合 | 一覧/本文の所在4通り、経路集合、通常ミラーの表示・操作優先、安定カーソル、掲載別集計・ピン、URI変更通知。旧APIは実在MiNoteの部分集合 |
| M8 | 投稿結果不明時も原本を増やさない | 両フォームの下書きに作成キーと入力ハッシュを保持し、本人＋キーでreceiptを照会。応答消失・再読込・相手停止でも確定済み結果を回収 |

## 後回しにする改善

| ID | 今回の扱い | 再検討する条件 |
| --- | --- | --- |
| D1 | 掲載解除後の本文URL・添付・縮小版・CDNの完全失効、未掲載原本の本人限定化は別案件 | 非公開/メンバー限定チャンネルや、掲載状態で本文の閲覧権を失わせる仕様を導入するとき |
| D2 | 全既存履歴のreplyId/threadId修復、過去返信件数の全面補正は別案件 | 既存データ修復の要件・対象・バックフィルを定めるとき。今回の新規投稿で親子関係を壊さず、件数を再送で二重加算しない条件はM5に残す |
| D3 | 通常AP投票全体の単一選択競合・全経路の排他方式の再設計は別案件 | 既存APの独立した不具合修正として扱う。新peer操作をAPと二重配送せず、同一actor/要求で重複させない対応はM6で行う |
| D4 | 全匿名閲覧へ新しい掲載証明を導入する方式と、その共有キャッシュ最適化は対象外 | D1の閲覧モデルを導入するとき。既存peerの頻度・サイズ・取得量制限は維持 |
| D5 | 停止や表示遅延に対する追加のUI改善、厳密な遡及ページ挿入は後続改善 | M7/M8で必須とするpending/failed/unavailable、再試行、重複防止の動作を確認した後に検討 |

D2/D3を延期しても、新方式が既存経路を悪化させない回帰確認は行う。新規データでも会話が独立投稿になる、操作が拒否される、二重反応・二重投票・二重通知が起きる場合は、その経路をM5/M6の不具合として修正する。将来の全面改善を延期することと、新方式の動作確認を省くことを混同しない。

## 基点と再利用する実装

れぞらぶは `codex/gridspace-bridge@57ee8ed337`、ぐりすぺは同ブランチの `9a15160548` を調査基点とする。計画用feat/multi-noteは旧基点なので実装前に既存ブリッジを取り込む。本番配備リビジョンは未確認。

既存のHMAC・nonce、アカウントリンク、通常共有ミラー、権限付き取得、guest返信、反応集合のrevision同期、統合タイムライン、URI重複除去、表示更新用DB outboxを再利用する。掲載配送は表示outboxとは別の永続キューにする。ActivityPubのオブジェクト形式は変更せず、通常の連合可否は通常投稿先・公開範囲・localOnlyで判定する。

固定ペアの署名付き操作だけを受理し、新ルートのplaceは送信originと原本originの一致、本人作成と保存した来歴を検査する。旧guest原本・専用返信にはauthorOriginの一致を要求しない。URIは設定済みoriginの許可されたnotesパスだけを受け、第三者URI・認証情報・不正なquery/fragmentを拒否する。既存のactivity別名の正規化をハッシュ・一意制約・ロックより先に行う。nonceと業務request IDは別に検査する。来歴・掲載情報の追加交換は内部peerメタデータで行い、APオブジェクトへは載せない。

## 原本・actor・既存API

新しいルート原本は現在ログイン中の投稿者のホームに1件作る。相手チャンネルを選んでもlinkedの別actorへ切り替えない。新UIは相手1チャンネルだけの場合も新掲載APIを使う。

旧channel-postは既存クライアント・iOS向けに従来の相手側作成を維持する。旧guest原本と専用会話のguest返信ではnoteOriginとauthorOriginが異なる。原本originは正規URIから決め、作者URIから推測しない。新ルート・専用返信の来歴はサーバー側で保存し、親削除後も本人削除を判定可能にする。保存方法は段階2で固定し、旧データを新来歴と誤認しない。

| 種別 | 原本の所在 | 操作actor |
| --- | --- | --- |
| 新しいルート原本 | 投稿者のホーム | 現在のローカルactor |
| 旧単一チャンネル投稿 | 従来のチャンネル提供側 | 既存guest actor |
| 通常投稿先ありの親への返信 | 返信者のホーム | 現在のローカルactor |
| 新しい専用会話の返信・子孫 | 会話ルート原本側 | 本人URIに対応するguestまたはローカルactor |

新capabilityとチャンネル提供/利用の能力を両側に追加する。ChannelAuthのclient/source、ChannelServiceのinitiator、PrivateServiceのrole/initiator/collectionClient、Linkのgrant/read/notify、Replyと通知のguest解決を監査する。旧private・collection・リンクの役割を全体で変更せず、新しいguest認可を分離する。

新しいフォロー・お気に入り・ミュートは現在actorの状態として保存する。リンク先の状態は自動移動せず、既存インポートで移せる公開状態のみ本人の明示操作で扱う。linkedの別actorを同一人物として反応・票数へ統合しない。正の権限をリンクで合算せず、既存のブロック・失効条件を維持する。

## 保存記録と作成

| 記録 | 所在と制約 |
| --- | --- |
| note | 原本側。本文・CW・添付・アンケートと通常投稿先。専用原本/会話内返信はincludeDefault=false、localOnly=true、gridspaceShared=false |
| note_channel_placement | ローカル掲載。noteId、channelId、canonicalUri、sortAt、状態・解除主体。(noteId, channelId)と(channelId, canonicalUri)が一意。原本削除時はSET NULLで最小記録を残す |
| gridspace_channel_placement | 相手原本の掲載。placementId、channelId、canonicalUri、noteOrigin、originNoteId、authorUri/authorOrigin、sortAt、sourceRevision/targetRevision、状態。(channelId, canonicalUri)一意 |
| 掲載先索引・希望状態 | 原本側。失敗・未配送も含む全宛先、世代、確定した掲載IDと状態。原本削除後も配送に使う |
| 作成/操作receipt | actor＋request ID、入力ハッシュ、結果URI、削除状態。同キーで異なる内容は競合。原本削除後も再作成しない |
| 掲載配送・状態返信 | 両側の永続キュー。原本側→希望状態/削除、チャンネル側→確定状態/管理者解除。状態変更と同じトランザクションに記録 |
| 削除・解除記録 | 原本削除は既存MiGridspaceNoteTombstoneの正規URIで統一。チャンネル解除は別のURI＋チャンネル単位 |
| channel_placement_pin | channelId、canonicalUri、rank。旧pinnedNoteIdsは実在MiNoteの部分集合として維持 |

相手原本の掲載にはローカルMiNoteを必須にしない。originNoteIdをローカルIDとしてJOIN・削除・ピン操作に使わない。掲載表・配送キューに本文・添付実体・認可tokenを保存しない。通常共有済みなら既存ミラーを使い、専用原本を表示するための通常ミラーは作らない。添付そのものの保管・公開URLは既存Driveに従う。

作成前に全ローカル宛先を検査し、全相手宛先をprepareする。初回prepare失敗は原本を確定せず下書きを保持する。成功後は原本、ローカル掲載、全宛先索引、receipt、配送ジョブを同じDBトランザクションで保存する。確定後の障害は同じ原本のpending/failedとして扱い、通常投稿先を補わない。

作成キーとハッシュは両フォームの下書きへ保存し、結果不明時は新しいキーを作る前に本人＋キーで照会する。receipt照会をprepareより先に行い、確定済みなら相手が停止中でも結果を返す。旧APIに新しいキーを必須化しない。

チャンネルを選ぶ場合はpublicを要求する。原本側・掲載側の禁止語、センシティブ語、公開投稿権限、ロール、停止・ブロック、頻度・サイズ・処理量制限を確認する。prepareでは本文/CW/アンケート文・添付メタデータを一時プレビューとハッシュで検査し、保存・ログ出力しない。placeで原本内容と現在の権限を再検査する。固定の掲載数上限は設けず、処理量制御と分割配送を使う。

本文編集・掲載後の宛先追加は初期対象外。「削除して編集」は新URI・新作成キーで候補を全件再認可する。予約確定も初期版ではサーバー側で拒否する。

## 掲載・取得・書込の契約

| 操作案 | 内容 |
| --- | --- |
| prepare/place | 原本側→掲載側。現在actor、対象、内容、希望チャンネル集合、sourceRevisionを検証して掲載を確定 |
| request-status | 本人＋作成キーで既存receiptを照会。原本URIをまだ知らないフォームの復旧に使う |
| status/sync | 原本URIの希望状態/確定状態、両側の世代を照合。本文なし |
| read/thread/file | 原本のある側から、既存の公開・利用者別条件で本文/会話/添付情報を取得。公開の直接取得に有効掲載を必須化しない |
| reply/upload/react/vote | 既存の操作権限と新形式の来歴・対象を検証。掲載の閲覧証明だけで書込を許可しない |
| delete-reply | 原本側で来歴と本人URIを確認し、本人の専用返信だけを削除。親・掲載の存続は不要 |
| remove/delete-origin | 掲載解除と原本削除を分離。原本削除は未掲載でもURI単位の終端状態を作る |

チャンネル文脈の証明はviewerActorUri、canonicalUri、channelOrigin/channelId、placementId、sourceRevision/targetRevision、用途・許可操作、expiresAtに結び付ける。用途はreadとreply/upload等を区別し、許可操作は掲載側が現在のポリシーで発行する。既存の60秒以内の再認可間隔を維持し、原本側も署名・利用者・対象・世代・用途・期限を照合する。read専用証明は書込へ流用できない。

掲載証明は一覧の正当な掲載文脈と書込条件を確認するために使う。公開原本の直接閲覧を有効掲載だけに依存させない。既存の停止・非表示時刻・サインイン要求・ブロック等は、通常取得と掲載経由の取得の両方で適用する。

アーカイブ済みチャンネルは従来どおり閲覧でき、新規掲載・返信・その返信用アップロードは拒否する。専用会話への返信は別の書込可能な有効掲載があればその経路を選び、全掲載が解除/アーカイブ済みなら返信を拒否する。通常投稿先ありの原本への通常返信は既存ルールを維持する。反応・投票はそれぞれの既存操作条件を適用する。DB確定前に証明を取得し、確定時に原本の存否・ローカル状態・期限を再検査する。

## 一覧の所在と表示・操作先

新参照はcanonicalUri、noteOrigin/originNoteId、channelOrigin/channelId、placementId、世代を分ける。既存sourceの意味を変えるだけでは対応しない。参照とカーソルはバージョンを分け、viewer/sessionに結び付ける。

| 一覧 | 本文 | 取得方法 |
| --- | --- | --- |
| local | local | ローカル掲載を確認し、原本を直接読む |
| peer | local | peerの掲載参照を確認し、local原本を直接読む |
| local | peer | local掲載を確認し、peer原本を直接読む |
| peer | peer | peerで掲載を確認し、その原本を読む |

原本の識別はcanonical URIで固定し、利用可能な経路の集合を保持する。通常原本の表示・myReaction・操作IDは閲覧側の実在ミラーを優先する。assertOwnersを拡張するのは経路集合と参照の扱いで、通常系のlocal優先表示・操作は維持する。ミラー未取得なら取込み前は読み取り専用にし、通常反応をguest向けActionServiceへ誤配送しない。

専用原本は委譲表示を使い、本文の所在へ1往復で取得する。peer一覧のlocal原本を再びpeerへ委譲して循環させない。原本URIの重複除去と表示経路を分け、片経路の解除・ミュートで他の有効経路まで消さない。一時不可を原本削除・掲載解除・返信0件とみなさない。

直接URL・notes/show・children/conversation・SSR・公開リンク・embedは既存の公開条件で読む。新しい掲載閲覧認可サービスを全packへ差し込む計画は取り下げる。Query/Entity/shouldHideNote/skipHide/ストリームの変更は、配信先判定と既存制限の維持に必要な範囲に限定する。内部packをそのまま通常TL等へ送らず、送信先ごとにincludeDefaultまたは有効掲載を検査する。

## 会話・反応・投票・添付

通常原本への返信は返信者側に親の通常ミラーを確保し、ローカルreplyIdで作る。今回の新規作成/署名付き取込では親の一時不可・未解決を既知削除と区別し、親未解決の子を独立投稿として確定しない。必要なら取込み全体を再試行し、通常localOnly親でも同じ会話へ戻ることを確認する。新規データの履歴先着/ライブ先着で親子関係・件数を一度だけ反映し、通知を再発行しない。全既存履歴の修復はD2とする。

専用会話の返信・子孫はルート原本側で保存する。peerReplyのguest actor・receipt・ローカルreplyId/threadId・原本側添付を拡張し、URIだけの親参照・分散返信索引は作らない。返信はincludeDefault=false、localOnly=true、gridspaceShared=false、独立した掲載先0件とする。チャンネルを開いた一覧では、ルートの有効な掲載先を引き継ぎ、返信自身の作成時刻で表示する。返信にもチャンネルのチップを付けるが、掲載解除・再送の管理権限は付けない。両サイトの原本から返信を取得し、すでに保存済みの返信にも適用する。ルートと返信の両方について現在の閲覧条件を確認し、通常TL・ホームへの独立配信・AP配送は増やさない。本文の閲覧は既存の公開条件に従い、親/掲載消失後の単体取得も本人だけに限定しない。guestがホーム側から自分の返信を開いて削除できる導線は用意する。旧単一チャンネル返信のチャンネル継承は維持する。

delete-replyはサーバー保存の来歴と投稿者URIを確認し、NoteDeleteServiceの認可コールバックで再確認する。他人の返信やルートをこの権限で消せない。アップロードはActionServiceのuploadSource/lockUpload/peerUploadに会話ルート・本人・用途別の書込許可を渡す。ファイル保管元、公開URL、サムネイルと再利用は既存方式を維持し、期限付き配信基盤は作らない。

通常リアクションは行為者ホームが所有する完全な集合とrevision同期を維持する。専用系は原本側の同じactor URIへ集約する。supportsGridspaceReactions/ChannelReactions、Action/Private、ReactionDeliveryService、ReactionNotificationService.receive、ExtendedReactionServiceの追加/解除を新来歴で分類する。channelId=nullだけで通常系に流さず、同じ対象へ両方の配送を適用しない。

通常の連合可能な投票は既存の標準API/AP経路を維持する。ペア内のlocalOnly原本と専用原本は署名付き操作で原本側へ投票し、guestのchannelIdガードを認可済み新形式に対応させる。原本のロック付き処理・actor解決・既存の一意性/単一選択/期限を使い、新peer操作をAPへ二重配送しない。票数・本人の選択状態は原本の結果を新UI/該当ミラー表示へ反映する。既存AP受信全体の排他再設計はD3。ActivityPubオブジェクト形式を追加しない。

通知は通常系と専用系を分類し、原本側の通知ID・宛先actorで重複除去する。専用会話の返信・子孫・guest宛て反応を既存の限定通知取得/既読へ追加し、一般受信箱を開放しない。通知本文・入れ子・ストリーム更新は既存の閲覧条件を確認する。チャンネル一覧からの解除は直接ノート購読の公開条件まで失効させる意味にしない。

## 削除と永続配送

原本側がURI＋相手originごとの希望集合とsourceRevision、掲載側が確定・管理者解除とtargetRevisionを所有する。双方の状態返信を永続配送し、statusで結果不明を解消する。再開時の照合、上限付きバックオフ、failedからの本人/管理者再試行を実装する。

placeとdelete-originは同じ正規URIのロック、removeは同じロック順でURI＋チャンネル状態を更新する。掲載前に削除が届いてもMiGridspaceNoteTombstoneへ記録し、後から大きな世代のplaceでも復活させない。通常ミラー取込と掲載操作は同じ墓標を検査する。管理者解除は当該掲載の終端状態とし、原本墓標へ書かない。

個別削除とDeleteAccountProcessorServiceの一括削除で同じ最小削除記録・全予定宛先の配送を作る。gridspaceShared=falseも対象とし、ユーザー行を消した後も削除配送を再開できるようにする。掲載、件数、ピン、索引を収束させる。DB状態、receipt、更新適用記録、表示outboxは同じトランザクションへ入れ、Redis等は安定イベントIDで重複除去する。

最小の作成receipt・URI墓標・解除記録は初期版では期限なし。本文・tokenは持たず、アカウント削除時の個人情報は既存方針で扱う。保持短縮は古い配送で復活しない条件を検証してから行う。

## 一覧・互換・変更通知

新一覧はローカル/相手とも原本時刻sortAt＋canonical URIのC照合降順で並べる。ローカル掲載にもキーを保存し、既存IdServiceと正規URI生成で作成/バックフィルする。activeの(channelId, sortAt DESC, canonicalUri DESC)索引を使い、段階1の旧note ID順とはカーソル版を分ける。遅延掲載は原本時刻の位置へ反映し、更新案内と再読込で収束させる。

相手の原本時刻は署名情報・ID時刻と整合を確認し、既存の時計ずれ許容を適用する。正当な遅延原本は古い時刻でも受け付け、受信時刻で最新扱いに変えない。

集計・ランキング・lastNotedAt・ピンは有効掲載をURI単位で数える。新ピン表と旧pinnedNoteIdsを同期し、旧APIは実在MiNoteと通常ミラーで表せる部分集合だけを返す。旧更新で見えないピンを消さず、専用本文を表示するための通常ミラーや偽IDは作らない。新掲載の作成は双方の統合タイムライン/capabilityが有効な場合に限る。

place-add/place-remove/origin-delete/place-policy等のURI必須イベントを既存outbox/changeへ記録する。両表へchannelOrigin/channelId/sourceRevision/targetRevisionと一意eventIdを追加し、適用対象のイベントに必要な値を必須化する。ローカルnote IDがない掲載もHTTP差分で追跡する。Redisには本文や個人用証明を入れない。

掲載解除は一覧・経路・チップ・ピンへ反映し、公開原本の本文を一律に隠す通知として扱わない。掲載側が停止したときはチップの状態を確認不能と表示し、0件/解除と誤認しない。存在しない掲載先名を推測せず、既存の利用者別表示制限を維持する。

## UIと下書き

投稿欄は通常投稿先とorigin付きチャンネルを独立に選び、空の投稿先は拒否する。チャンネル画面は当該チャンネルだけを初期選択とし、通常投稿先を追加できる。多数の選択は折りたたみ表示し、製品上の固定上限にはしない。

送信前の失敗は下書きを保持する。原本確定後は本文確定と掲載先別pending/active/failed/removedを分け、管理画面から掲載だけを再試行する。確定待ち作成キーは結果照会まで保持し、原本を再投稿しない。

専用投稿には「チャンネルだけに掲載します。公開範囲と添付URLは既存の公開チャンネルと同じです」と案内する。解除時は「このチャンネルの一覧から外します。投稿本体は残ります」、未掲載時は「本文は確定しています。未掲載でもURLから開ける場合があります」と示す。非公開・本人限定と誤解させる表示をしない。

## 実装順序と有効化

1. 最新ブリッジへ基点をそろえ、来歴・capability・本人性・用途別書込証明と保存方法を両側で固定する。
2. ローカル保存と配信先判定、RSS・通常共有、既存閲覧制限、操作の新旧分類、削除/一括削除を実装する。旧worker停止・移行・照合後にM1/M2/M4を検証する。
3. prepare/place/request-status/status/remove/delete-originと両側の永続配送、receipt・墓標を実装する。
4. 所在4通りの一覧・表示/操作先、URIカーソル、集計・ピン、旧API部分集合、変更通知とUIを実装する。
5. 両方向の返信・guest削除/添付/通知、反応・投票、通常localOnly、新規履歴先着/ライブ先着を検証する。
6. 対象機能のM1〜M8と上記の更新要件が通った範囲だけ新規書込を限定有効化する。D1〜D5は有効化条件にしない。停止は新規書込を止め、既存データの読取・削除配送は残す。

| 受け入れ条件 | 確認する結果 |
| --- | --- |
| 配信と公開を分離 | 専用原本/返信は通常TL・RSS・通常共有・AP自動配送へ出ない。一方、URL/標準APIは掲載解除前後とも既存の公開条件で読める |
| 一覧/本人性 | 両方向、同名/同ID、一覧/本文4通り、複数フォローとミュートでURI1行を維持し、actorや操作先を取り違えない |
| 閲覧制限と書込 | 停止・非表示時刻・ブロック・サインイン要求をpack/SSR/通知/ストリームでも維持。read証明で書込できず、全掲載アーカイブ後の返信/添付は拒否 |
| 会話と操作 | 通常返信のreplyId/threadId/inReplyTo、専用子孫の原本側保存、本人削除・添付・通知・既読、反応追加/解除と原本投票が両方向で成立 |
| 削除と再送 | place前の原本削除、逆順/高世代再送、相手停止中の退会、一括削除でも復活せず、掲載・件数・ピンが収束 |
| フォーム復旧 | 作成確定直後の応答消失と再読込で同じキーを復元し、相手prepare停止中でもreceiptから結果を回収。原本・通知を増やさない |
| 互換と停止 | 旧API/クライアントは実在行の部分集合を扱い、新旧書込workerの混在を終えてから有効化。停止後も読取・削除配送を維持 |

新規書込前の残判断はincludeDefault移行時の既存CHECK違反の処置、canPublicNoteと専用投稿の関係、allowRenoteToExternalと通常投稿先の組合せ、通常検索/推薦の旧投稿との整合。M1〜M8の実装と両側の検証が済むまで有効化しない。計画改訂は実装・配備・テスト完了を意味しない。
